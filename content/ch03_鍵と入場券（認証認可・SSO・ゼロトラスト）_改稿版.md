# 鍵と入場券（改稿版）

## 第一章　鍵と部屋

　早瀬が Snowflake のアカウントを欲しがったのは、入社から半年が過ぎた十月のことだった。

「佐伯さんに毎回 SQL を頼むのが申し訳なくて。自分で叩けるようになりたいんです」

　赤海は三秒ほど早瀬の顔を見て、それからキーボードに向かった。今日のからあげ棒は、赤い。何味かは聞かなかった。

```
CREATE USER hayase
  PASSWORD = '********'
  DEFAULT_ROLE = analyst
  MUST_CHANGE_PASSWORD = TRUE;

GRANT ROLE analyst TO USER hayase;
```

「作った。初回ログインでパスワードを変えろ」

「はい！」

　早瀬は自席に戻り、Snowflake のログイン画面を開いた。ユーザー名、パスワード。入る。パスワード変更を求められ、変える。画面が開いた。

　左側にデータベースの一覧が出る。MARTS というデータベースを開くと、SALES、MARKETING というスキーマがある。SALES の中に mart_sales_monthly があった。三上部長が六十回押しているグラフの元になった表だ。早瀬は嬉しくなって、SQL を打った。

```
SELECT * FROM marts.sales.mart_sales_monthly LIMIT 10;
```

　結果が出た。

　次に、経理の橘が見ている表を見てみたくなった。見てはいけない理由が、早瀬には思いつかなかった。

```
SELECT * FROM marts.finance.mart_revenue_recognition LIMIT 10;
```

```
SQL access control error: Insufficient privileges to operate on schema 'FINANCE'
```

　早瀬は小部屋に戻った。

「経理の表が見えません。ログインはできてるのに」

「ログインできてることと、見えることは、別だ」

　赤海はホワイトボードに二つの言葉を書いた。この小部屋のホワイトボードは、いつも二つの言葉から始まる。梨乃はそれを「赤海の二行」と呼んでいる。

```
認証（Authentication）＝ あなたが誰かを確かめる
認可（Authorization）  ＝ その誰かに何を許すかを決める
```

「わかりました！」

　早瀬が言った。

「認証と認可は、同じものの、言い方の違いですね！」

「違う」

「……今日も、ですか」

「今日もだ」

　早瀬は最近、外すことに慣れてきていた。慣れるべきかどうかは、梨乃にもわからなかった。

「ログイン画面でパスワードを入れて通ったのは、認証だ。Snowflake は『この人は hayase だ』と確認した。それだけだ。hayase が経理の表を見ていいかどうかは、別の話で、それは認可という」

「認可は、どこで決まってるんですか」

「ロールだ」

　赤海はもう一つ画面を出した。

```
ROLE analyst
  ├─ USAGE  on DATABASE marts
  ├─ USAGE  on SCHEMA marts.sales
  ├─ SELECT on ALL TABLES in marts.sales
  ├─ USAGE  on SCHEMA marts.marketing
  └─ SELECT on ALL TABLES in marts.marketing

ROLE finance
  ├─ USAGE  on SCHEMA marts.finance
  └─ SELECT on ALL TABLES in marts.finance
```

「hayase には analyst というロールがついてる。analyst は sales と marketing のスキーマを読める。finance は読めない。finance を読めるのは finance ロールで、それを持ってるのは橘さんと俺だけだ」

「僕が finance を見たいときは」

「橘さんが『いい』と言ったら、俺が GRANT する。誰が何を見ていいかを決めるのは、俺じゃなくて、その表のオーナーだ。前回、決めた」

「橘さんが『いい』って言ったこと、ありますか」

「ない」

「じゃあ一生見られない」

「一生の話はしてない」

　早瀬はメモした。

> 認証＝誰か。認可＝何ができるか。
> ログインできる≠何でも見られる。
> （橘さんの「いい」は前例がない）

「もう一つ聞いていいですか。ログインのとき、パスワードは Snowflake のどこに保存されてるんですか。赤海さんが最初に決めたパスワードを、赤海さんは見られるんですか」

　赤海は少し嬉しそうな顔をした。からあげ棒を、少しだけ早瀬のほうに傾けた。差し出すほどではなかった。

「見られない。まともなシステムは、パスワードをそのまま保存しない」

「じゃあ、どうやって合ってるかわかるんですか」

「ハッシュという一方向の計算を通す。パスワードが 'yamabiko2026' だとすると、それを bcrypt という計算にかけると、こういう文字列になる」

```
$2b$12$KIXw7p3h9JgQhYdF1mRz.eZ6rKfJqO3n8xB4wLcD0aH2sV5tG7yUm
```

「この文字列から、元のパスワードには戻せない。だがもう一度 'yamabiko2026' を同じ計算にかければ、同じ文字列になる。Snowflake は、この文字列だけを保存してる。ログイン時に入力されたものを計算して、保存してある文字列と比べる。一致すれば通す」

「じゃあ、Snowflake のデータベースが丸ごと盗まれても、パスワードは漏れない」

「漏れにくい。短いパスワードは、総当たりで元を推測できる。だから長くしろと言われる」

「三上部長のパスワードは、たぶん短いです」

「なぜわかる」

「先週、部長が『パスワードは全部テントだ』と言ってました」

　赤海は何も言わなかった。串を缶に立てる音だけがした。

「ログインした後は？　毎回パスワードを送ってるんですか」

「送ってない。一回認証が通ったら、Snowflake は『セッション』を作って、その番号をブラウザに渡す。ブラウザはそれ以降、その番号を毎回送る」

　赤海はブラウザの開発者ツールを開いて、Cookie の欄を見せた。

```
Cookie: snowflake_session=a8f3c2e1-4b7d-4e9a-9c1f-2d8e5f6a7b3c
```

「この番号が『あなたはさっき認証を通った hayase だ』という証拠になる。ブラウザを閉じるか、一定時間たつと、番号は無効になる。また最初からログインだ」

　早瀬は開発者ツールの画面を、しばらく眺めていた。

「ヤマビコストアのお客さんも、同じですか」

「同じだ。お客さんが会員 ID とパスワードを入れると、EC の会員データベースにあるハッシュと比べて、通ればセッション番号を Cookie に入れる。カートに商品を入れる操作は、全部そのセッション番号で『誰のカートか』を判別してる」

「じゃあ、三上部長がテントを入れてるカートも、セッション番号で」

「三つのセッションだ。三つのアカウントだから」

「名寄せしたのに」

「DWH の上では一人だ。EC の上では、まだ三人だ。それを一人にするのが、今日の話の、次の段階になる」

　梨乃が小部屋に入ってきた。

「その話、ちょうど聞きたかったんです。マーケの森田さんが『Google でログイン』を付けたいと言ってて。ログインが面倒で会員登録を離脱する人が三割いるらしくて」

「それは、ヤマビコストアが自分でパスワードを確かめるのをやめて、Google に確かめてもらう話だ。今の話の、次の次の段階になる」

「段階が多いですね」

「多い。その前に、もっと急ぎの話がある。総務の岡崎さんから、今朝、相談が来た」

「岡崎さんから？」

「Q1 で止まったそうだ」

「Q1？」

「行けばわかる」

## 第二章　十二個のパスワード

　総務の岡崎は五十代で、ヤマビコの総務と経理補助と、そして「情シス」を兼務している。

　情シスといっても、パソコンの調達と、SaaS のアカウント発行と、Wi-Fi のパスワードを聞かれたら答えることが主な仕事だ。あと、夜座コンサルティングの契約書を持っている。件名は「調査」のままだ。

「これ、どうしたらいいのか、わからなくて」

　岡崎が赤海と梨乃に見せたのは、大手百貨店「丸嘉」から届いた書類だった。

　丸嘉はヤマビコの商品を自社のオンラインストアで販売したいと言ってきており、そのためには丸嘉のシステムからヤマビコの在庫を参照する仕組みが要る。商談は順調だったが、丸嘉の情報システム部門から「セキュリティチェックシート」が送られてきた。

　八十項目。

「Q1 で止まった、と聞きました」

「はい」

「Q1 は何ですか」

「会社名を書く欄です」

「……なんで止まるんですか」

「『株式会社』を前に付けるか後ろに付けるか、迷って。登記は前なんですけど、丸嘉さんとの契約書では後ろになってて。どっちを正式とするか、私が決めていいのかわからなくて」

　梨乃は、志村の「本当の最新」を思い出した。岡崎は岡崎で、正本を探していた。

「登記の通りで。次は」

「Q12 からです」

```
Q12. 従業員の退職時、アカウントは何営業日以内に無効化されますか。
Q13. 業務システムへのログインに多要素認証（MFA）を導入していますか。
Q14. 業務システムのアカウントは統合ID基盤（IdP）で一元管理されていますか。
Q15. 業務システムへのアクセスにシングルサインオン（SSO）を利用していますか。
Q31. 社外からの社内システムへのアクセスは、どのように制御されていますか。
Q32. 業務端末の管理（MDM）を導入していますか。
...
```

「Q12 から、もう答えられないんです」

　岡崎は自分のノートパソコンを開いた。Excel が立ち上がった。ファイル名は「アカウント台帳_2026.xlsx」だった。

　梨乃と赤海は顔を見合わせた。田中さんの Excel、志村さんの本当の最新、そして岡崎さんの台帳。三つ目だ。

「これに、誰がどのサービスのアカウントを持ってるか、書いてあります。Microsoft 365、Slack、Snowflake、Power BI、EC の管理画面、倉庫システム、会計システム、勤怠、経費精算、採用管理、広告管理、あと社内 Wi-Fi。十二個」

「六十人で十二個だから、七百二十行」

「はい。ただ、全部のサービスの管理画面を見に行かないと、本当に合ってるかはわからなくて」

　赤海が聞いた。

「退職者は」

「退職の連絡が来たら、私が十二個のサービスの管理画面に順番に入って、消しています。ただ、去年の暮れは忙しくて」

　岡崎は言いにくそうに言った。

「田中さんの Snowflake のアカウント、まだ残ってました。先週気づきました」

　小部屋が静かになった。串の缶が、少しだけ鳴った。

「田中さんは、Snowflake を使ったことは？」

「一度もないと思います。赤海さんが去年、営業マートを見せるために作って、田中さんは結局 Power BI のほうを見てたので」

「田中さん、緑茶と Excel しか使ってなかったですもんね」

　梨乃が言った。

「ログイン履歴を見る」

　赤海は Snowflake の管理画面を開いた。tanaka というユーザーの最終ログインは、去年の十一月。それ以降はなかった。

「使われてない。だが、使われてない、というのは、俺がたった今、見に行ったからわかったことだ。田中さんのパスワードは田中さんしか知らない。田中さんがメモをどこかに残してたら、誰でも入れた」

「田中さんは、メモを残す人ですか」

「四十ページのマニュアルを書く人だ」

「……残してますね」

　赤海は tanaka を無効化した。

「岡崎さん、これは岡崎さんの落ち度じゃない。十二個のサービスの管理画面を一つずつ見に行く仕組みのほうが、無理だ」

「じゃあ、どうすれば」

「前回と同じことをやる」

　赤海はホワイトボードに、前回の図を描いた。真ん中に「商品マスタ（正本）」。周りに五つのシステム。矢印は正本から外へ。

　そして「商品マスタ」を消して、「人のマスタ（正本）」と書き直した。周りの五つを十二に増やした。

「今のヤマビコは、十二個のサービスに、十二個の『人の登録』がある。商品が五か所に五つのコードで登録されてたのと、まったく同じ構造だ。岡崎さんの Excel は、志村さんの台帳と同じで、十二か所を写した台帳だ。正本ではない」

「私の台帳も、写しですか」

「写しです」

「……本当の最新、にしたら」

「名前を変えても写しです」

　岡崎は少しがっかりした。志村の命名法は、総務にまで広まっていた。

「正本を作る」

　梨乃が言った。

「そうだ。人の正本を作り、そこから十二個のサービスに配る。入社したら正本に一回登録し、十二個に自動で増える。退職したら正本で一回無効にし、十二個で自動で消える。人の正本のことを、ディレクトリ、あるいは IdP という。アイデンティティ・プロバイダ。『あなたが誰か』を提供する場所」

「製品はあるんですか」

「ある。ヤマビコはメールが Microsoft 365 だから、Entra ID が最初からついてくる。旧称は Azure AD。他には Okta、Google Workspace のディレクトリ、JumpCloud」

「Entra ID は、もう使ってるってことですか」

「メールと Teams のログインには、すでに使ってる。ただ、他の十一個のサービスは、Entra ID を知らない。それぞれが自分でパスワードを持って、自分で認証してる。これを、『十一個のサービスが Entra ID に認証を任せる』形にする」

「それが、SSO」

　岡崎がチェックシートの Q15 を指した。

「シングルサインオン。一回サインオンすれば、全部に入れる」

　早瀬が小部屋の入口から顔を出した。いつの間にか聞いていた。

「SSO って、Super Strong……」

「シングル・サイン・オン」

「……はい」

　赤海は頷いた。

「ただし、『一回でいい』は結果であって、本質じゃない。本質は、パスワードを確かめる場所が一か所になることだ。田中さんのパスワードは、Snowflake の中ではなく、Entra ID の中にだけ存在するようになる。Entra ID で田中さんを無効にすれば、Snowflake にも Slack にも入れない。Snowflake はパスワードを持ってないからだ」

「Snowflake がパスワードを持ってないのに、どうやって本人だとわかるんですか」

　早瀬が聞いた。

「それが、今日の午後の話だ。岡崎さんも来てください。設定は岡崎さんにやってもらう」

「私が？」

「これは岡崎さんの仕事になる。俺は手伝うだけだ」

「私、Q1 で止まる人ですよ」

「Q1 は、もう通りました」

　岡崎は「わかりました」と言った。

　岡崎の「わかりました」は、三上の「わかった！」とは違う。本当にわかっていて、本当にやる。そのことを、赤海は知っていた。

　その日の昼、梨乃は廊下で社長に捕まった。

「丸嘉の件、どうなってる」

「セキュリティチェックシートが八十項目あって、今、Q15 あたりです」

「セキュリティってのはな」

　来た、と梨乃は思った。

「家の鍵みたいなもんだ。家には……鍵がある」

「はい」

「鍵は、一本のほうがいい」

　梨乃は一瞬、止まった。

「……一本ですか」

「十二本も持ってたら、どれがどれかわからんだろう」

　社長はコーヒーを飲んで、歩いていった。

　梨乃はメモ帳に「鍵は一本（社長）」と書いた。SSO のことを、社長は知らないはずだった。今回も、当たる半分だったらしい。

## 第三章　三回の往復

　午後、小部屋には岡崎と早瀬と梨乃がいた。赤海は一番大きなモニターに、二つの管理画面を並べた。左が Entra ID、右が Snowflake。

「まず言葉を二つ」

「赤海の二行だ」と梨乃が小声で言い、早瀬が頷いた。

「これから Snowflake は、認証を Entra ID に任せる。任せる側の Snowflake を SP、サービス・プロバイダという。任される側の Entra ID を IdP という。この二つが信頼関係を結ぶ手続きを、SAML という規格で行う」

「サムル」

「サムル。二〇〇五年にできた古い規格だ。古いが、企業向けの SaaS はほぼ全部これに対応してる。岡崎さん、右の Snowflake の管理画面で、『SAML』と書いてある設定を開いてください」

　岡崎がクリックすると、いくつかの入力欄と、二つの長い文字列が表示された。

```
Snowflake側（SP）が教えてくれる情報
  Entity ID:  https://yamabiko.snowflakecomputing.com
  ACS URL:    https://yamabiko.snowflakecomputing.com/fed/login
```

「この二つを控えてください。Entity ID は Snowflake の名前。ACS URL は、『認証が終わったら、ここに結果を届けてくれ』という宛先です」

　岡崎は慎重にメモした。手書きだった。赤海は「コピーでいいです」と言い、岡崎は「手で書いたほうが覚えるので」と答えた。

「次に左の Entra ID で、『エンタープライズ アプリケーション』から Snowflake を追加します。そこにさっきの二つを貼る」

　岡崎が貼り終えると、今度は Entra ID 側が長い文字列を出した。

```
Entra ID側（IdP）が教えてくれる情報
  Login URL:      https://login.microsoftonline.com/xxxx/saml2
  Entity ID:      https://sts.windows.net/xxxx/
  署名証明書:      -----BEGIN CERTIFICATE----- MIIC8DCCAdig...
```

「これを Snowflake に貼り戻す。Login URL は『認証してほしいときは、ここに人を送れ』という宛先。証明書は、Entra ID の印鑑だ」

「印鑑」

　岡崎の目が少し輝いた。総務は印鑑に強い。

「後で出てきます。貼ってください」

　岡崎が貼り終え、保存した。両方の画面に「構成済み」と出た。

「終わりですか？」

「設定は終わりだ。あと、Entra ID 側で『誰がこのアプリを使えるか』を割り当てる。今は早瀬さんだけ」

「僕だけ」

「実験台だ」

「光栄です」

　赤海は早瀬に言った。

「Snowflake からログアウトして、もう一回ログイン画面を開いてくれ。そして今度はパスワードを入れずに、『SSO でサインイン』を押せ」

---

　早瀬は言われた通りにした。赤海は隣で、ブラウザの開発者ツールの「ネットワーク」タブを開いていた。

「これから起きることを、三回の往復として見せる。ブラウザが、Snowflake と Entra ID の間を、使いに走る」

「わかりました！」

　早瀬が言った。

「三回の往復ということは、六回移動するんですね！」

「……そういう数え方をするなら、そうだ」

「当たりましたか？」

「数え方の話だ」

　早瀬は数え方で当たったことにした。梨乃は何も言わなかった。

　早瀬が「SSO でサインイン」を押した。

「一回目」

　開発者ツールに、こう出た。

```
GET  https://yamabiko.snowflakecomputing.com/fed/login
  → 302 Redirect
  Location: https://login.microsoftonline.com/xxxx/saml2?SAMLRequest=fZJNb9swDIb...
```

「Snowflake は『俺はこの人を知らない。Entra ID に聞いてこい』と言って、ブラウザを Entra ID に追い返した。302 というのは『別の場所へ行け』という返事だ。行き先の URL に SAMLRequest という長い文字列がくっついてる。これは Snowflake から Entra ID への手紙で、中身を平文にするとこうだ」

```
<samlp:AuthnRequest
    ID="_a1b2c3d4"
    IssueInstant="2026-10-14T05:12:44Z"
    AssertionConsumerServiceURL="https://yamabiko.snowflakecomputing.com/fed/login">
  <saml:Issuer>https://yamabiko.snowflakecomputing.com</saml:Issuer>
</samlp:AuthnRequest>
```

「『Snowflake から。この人を認証して、結果はこの ACS URL に送ってくれ』と書いてある」

　早瀬のブラウザには、見慣れた Microsoft のログイン画面が出ていた。メールアドレスを入れ、パスワードを入れ、スマホの認証アプリに出た番号を入れた。

「二回目。今、早瀬さんは Entra ID に対してパスワードを入れた。Snowflake は関係ない。Snowflake はこの画面を見てもいないし、パスワードを受け取ってもいない」

　認証が通った。ブラウザが一瞬白くなり、Snowflake の画面が開いた。

「三回目。ここが本題だ」

　開発者ツールに、こう出た。

```

```

```
形式           XML                        JSON（JWT）
運ぶもの       アサーション                id_token
得意           企業の社員向け SaaS          消費者向けサイト・スマホアプリ・API
土台           単独                        OAuth 2.0 の上に載る
ヤマビコでは   社員→Entra ID→Snowflake等   お客さん→Google→ヤマビコストア
```

「Entra ID は両方できる。Snowflake も両方できる。だから社員のログインを OIDC でやることもできる。ただ、企業の SaaS の設定画面には『SAML』と書いてあることが多く、消費者向けの『○○でログイン』は全部 OIDC だ。使い分けは、規格の優劣ではなく、相手がどちらに対応してるかで決まる」

　森田は、少し安心した顔で言った。

「じゃあ、『Google でログイン』は、OAuth じゃなくて OIDC でやる、と」

「そう言うのが正確だ。ただし世間では『Google の OAuth ログイン』と呼ぶ人のほうが多い。土台が OAuth だからだ。中身は OIDC だと知ってればいい」

「私、来週のマーケ会議で『OIDC でやります』って言っていいですか」

「言っていい」

「かっこいいですよね、OIDC」

「かっこよさの話はしてない」

　森田は嬉しそうに出ていった。パソコンは持っていなかったので、電池は切れなかった。

　梨乃はノートに書いた。

> access_token ＝ 入場券。何をしていいか。持ち主の名前はない。
> id_token ＝ 名札。誰が、いつ、誰宛てに認証されたか。署名付き。aud を必ず確かめる。
> OAuth で「ログイン」してはいけない。OIDC を使う。
> SAML と OIDC は同じことをする二つの流儀。相手の対応で選ぶ。
> （Google の印鑑登録は役所が要らない。岡崎さんが羨ましがった）

## 第六章　城壁の内側

　十一月の第一週、倉庫で事故が起きた。

　倉庫の佐藤が、いつも通り朝八時に出荷指示を確認しようとして、倉庫システムの管理画面を開いた。出荷待ちの注文一覧に、見覚えのない配送先が並んでいた。二十件。全部、埼玉県内の同じ私書箱宛て。商品は全部、単価の高いテントとダウンジャケット。

　佐藤はすぐに出荷を止め、志村に電話し、志村が赤海に電話した。

　赤海は、小部屋から出た。二回目だった。

　倉庫システムのログを調べると、前日の夜十一時に、admin というユーザーが二十件の配送先を書き換えていた。admin のパスワードは、倉庫の共用パソコンのモニターに貼られた付箋に書いてあった。

「付箋、ですか」

「付箋です」

　佐藤は正直だった。

「何て書いてあるんですか」

「……yamabiko123 です」

「テントじゃないんですね」

「テントは部長のです」

　だが、書き換えは倉庫のパソコンからではなかった。VPN 経由で、社外から行われていた。

「VPN のアカウントは？」

「佐藤さんの」

　赤海は佐藤に、先週何かおかしなことがなかったか聞いた。佐藤は思い出した。三日前、「運送会社からの請求書」というメールが来て、添付を開いた。中身は空だった。

「空だったので、運送会社に『空でしたよ』って返信しました」

「返信したんですか」

「親切に」

「そのパソコンは、もう使わないでください」

　赤海は言った。それから小部屋に戻り、ホワイトボードに城の絵を描いた。絵は、あまり上手くなかった。

---

「今のヤマビコのネットワークは、こういう考え方でできてる」

　集まったのは、梨乃、早瀬、岡崎、そして倉庫の佐藤。志村もいた。志村はアイゼンを持ってきていた。理由は誰も聞かなかった。

「城壁がある。壁の内側が社内ネットワーク。壁の外がインターネット。壁には門が一つあって、VPN という。社外から入るには、門で VPN のパスワードを見せる。門を通ったら、中は自由だ。倉庫システムも、注文データベースの管理画面も、ファイルサーバーも、中からなら誰でも見える。中にいる人は味方だ、という前提で作られてる」

「境界防御、というやつですか」

　早瀬が言った。手は挙げなかった。当たった。

「そうだ。壁の外は敵、壁の内側は味方。二十年前はそれで良かった。社員は全員オフィスにいて、パソコンは全部会社支給で、システムは全部自社のサーバー室にあった」

「今は違う」

「今は、社員の半分が在宅で、Snowflake も Slack も Microsoft 365 も壁の外にあり、佐藤さんのパソコンはメールの添付一つで乗っ取られた。乗っ取られたパソコンは、壁の内側にいる。VPN の門を、佐藤さんの正規のアカウントで通ってくる。門番からは味方に見える」

　赤海は城の絵に、内側から倉庫システムへ伸びる矢印を描いた。

「門を通ったあと、倉庫システムは『中から来た人だ』というだけで、admin のパスワードを付箋から読んだ相手に、配送先の書き換えを許した。城壁の内側は信頼する、という前提が、そのまま被害になった」

　佐藤が小さな声で言った。

「すみません」

「佐藤さんの落ち度じゃない。添付を開いた人を責めるなら、六十人全員を責めることになる。三上部長は、先月『無料テント当選のお知らせ』を開いてる」

「開いたんですか」

「開いて、住所を入力しかけて、岡崎さんが止めた」

　岡崎が静かに頷いた。

「壁の内側なら信頼する、という設計のほうが、もう成り立たない」

　赤海は城の絵の横に、別の絵を描いた。城壁はなかった。代わりに、一つ一つの建物の前に、それぞれ門番が立っていた。門番の絵も、あまり上手くなかった。

「これがゼロトラストだ。『壁の内側だから信頼する』をやめる。倉庫システムも、注文データベースも、Snowflake も、一回一回のアクセスごとに、門番が確かめる」

```
ゼロトラストの門番が、毎回確かめること
--------------------------------------------------
誰が      IdP で認証された本人か。MFA を通ったか。
どの端末で 会社が管理している端末か。OS は最新か。
どこから  いつもの場所か。深夜の海外からではないか。
何を      その人のロールに、この操作の許可があるか。
```

「たとえば昨日の夜の出来事を、この門番に通すとどうなるか。『誰が』は佐藤さんの VPN アカウントで通る。しかし『どの端末で』で止まる。攻撃者のパソコンは、ヤマビコが管理してる端末ではない。門番は通さない」

「端末の管理って、どうやるんですか」

　岡崎が聞いた。赤海は少し、口の端を上げた。

「MDM という」

　小部屋に、微妙な空気が流れた。志村がアイゼンを持ったまま言った。

「マスタデータ管理？　私が登録画面で三百回やるやつ？」

「違う」

「違うのか」

「Mobile Device Management。端末管理。同じ略語で、まったく別のものだ。Intune や Jamf という製品で、会社のパソコンやスマホに小さな管理ソフトを入れて、『この端末は会社のものだ』という証明書を持たせる。門番はその証明書を見る」

「ややこしい」

「ややこしい。丸嘉のチェックシートの Q32 は、こっちの MDM だ」

　岡崎が、チェックシートに「MDM（端末のほう）」と書き込んだ。志村が「私のほうは何と書くんだ」と聞き、岡崎が「MDM（志村さんのほう）」と書いた。それで通じることになった。

　赤海は続けた。

「『どの端末で』の次に、『何を』でも止まる。admin という全能のアカウントを、付箋のパスワードで、深夜に、配送先の一括変更に使う。ゼロトラストでは、admin は存在しない。佐藤さんには『出荷指示を確認する』権限があり、志村さんには『商品を登録する』権限があるが、『二十件の配送先を一括で書き換える』権限は誰にもない。必要なら、その操作だけを、その日だけ、申請して許可される。最小権限という」

「三上部長の権限は」

　早瀬が聞いた。

「『営業マートを六十回押す』だ」

「それは、権限として設定できるんですか」

「回数は制限しない」

---

「具体的に、何をするんですか」

　梨乃が聞いた。赤海は四つ書いた。

```
1. VPN を廃止する。門をなくす。
2. 倉庫システム・会計システムの前に、門番を立てる。
   （Cloudflare Access / Entra ID の条件付きアクセス）
   門番は Entra ID で本人を確かめ、MFA を要求し、Intune の端末証明書を確かめる。
3. 全社員の端末に Intune を入れる。私物端末からは業務システムに入れない。
4. admin を廃止し、ロールに分ける。付箋を剥がす。
```

「二番の門番は、先月 SAML でやったことの延長だ。倉庫システムは古くて SAML に対応してない。だから倉庫システムの前に、対応してる門番を立て、門番が代わりに Entra ID と話す。倉庫システムから見れば、門番を通ってきた人しか来ない」

「VPN をなくして、大丈夫なんですか」

「VPN がなくなると、倉庫システムは『インターネットから直接見える』ようになる。ただし門番の後ろにいる。門番は、Entra ID を通り、MFA を通り、Intune の証明書を持つ端末からの通信だけを通す。攻撃者が佐藤さんのパスワードを盗んでも、スマホの MFA と会社の端末がなければ入れない。VPN の門一つで守るより、強い」

「MFA って、何ですか」

　佐藤が聞いた。

「多要素認証。パスワードの他に、スマホに出る番号も入れる」

「二段階ですね」

「二段階だ」

　そこへ、三上が入ってきた。狭い小部屋が、さらに狭くなった。志村のアイゼンが三上の靴に当たった。

「二段階？　一段階でいいだろう。面倒だ」

「一段階だと、部長のアカウントが三つになります」

「……それとこれとは」

「関係あります。パスワードを三回忘れて三つ作ったので、二段階目のスマホがあれば、忘れても本人だと確かめられます」

　三上は少し考えて、言った。

「わかった！」

　今回は、わかっていたかもしれなかった。梨乃には判断がつかなかった。

「壁がないのが、逆に安全」

　早瀬が言った。

「壁がないのではない。壁が、システム一つ一つの目の前まで下がった。城壁を守る代わりに、部屋ごとに鍵をかけた」

　赤海はホワイトボードの、城壁のない絵を指した。

「ゼロトラストは製品ではない。考え方だ。Okta や Entra ID や Cloudflare や Zscaler は、その考え方を実装するための道具で、『ゼロトラスト製品を買えば終わり』ではない。『壁の内側は信頼する』という前提を、設計から取り除くことだ」

　岡崎がチェックシートを開いた。Q31、社外からのアクセス制御。Q32、端末管理（端末のほう）。Q13、MFA。Q14、IdP。Q15、SSO。

「これ、全部つながってたんですね」

「つながってる。丸嘉の情シスは、『壁の内側を信頼してないか』を八十項目で聞いてる」

「Q1 は？」

　早瀬が聞いた。

「Q1 は、会社名だ」

「それは、つながってないですね」

「つながってない」

　岡崎は、Q1 の欄に、登記の通り「株式会社ヤマビコ」と書いた。丸嘉との契約書のほうは、来年、直すことにした。

## 終章　月曜の朝

　十二月の第一月曜日、朝八時。早瀬は自宅で、会社支給のノートパソコンを開いた。

　赤海がその日の午後、早瀬に「今朝、Power BI を開いたとき、何が起きたか説明できるか」と聞いた。早瀬は、二か月前に貼った図の前に立った。図の隅には、付箋が三枚増えていた。「※部長の Google は二つ」「※MDM は二つ」「※Q1 は会社名」。

「まず、パソコンを開いたとき、Intune が『この端末は会社のもので、OS は最新で、ディスクは暗号化されている』という証明書を持っていることを確認しました。これが端末の門番です」

「次に、ブラウザで Power BI を開きました。Power BI は Entra ID に認証を任せているので、Entra ID のログイン画面が出ました。パスワードを入れて、スマホの認証アプリの番号を入れました。これが認証で、MFA です。二段階です。Entra ID は、端末の証明書と、私がいつも使う東京からのアクセスであることも見ました。条件付きアクセスです」

「Entra ID は Power BI に、『この人は hayase@yamabiko.co.jp だ』という署名付きの手紙を、ブラウザ経由で届けました。印鑑です。Power BI は署名を確かめて、セッションを作りました。パスワードは Power BI を通っていません」

「Power BI は、営業マートのグラフを描くために、Snowflake に問い合わせました。このとき Power BI は、私のパスワードではなく、Power BI 自身に発行された OAuth の入場券を使いました。人がいないので、クライアント・クレデンシャルです。scope は marts:read」

「Snowflake は入場券を確かめて、Power BI に許されたロールで問い合わせを受けました。ただし、私が経理マートのページを開こうとしたら、Power BI の側で『hayase は finance ロールを持たない』と判定して、ページ自体が出ませんでした。これが認可です。橘さんの『いい』は、まだ前例がありません」

「だから、私は営業マートの棒グラフだけを見ました」

　赤海は何も言わなかった。早瀬は続けた。

「一回の『Power BI を開く』の裏で、端末の確認が一回、認証が一回、MFA が一回、SAML の手紙が一往復、OAuth の入場券が一回、認可の判定が一回。六つの確認を通って、棒グラフが一枚出た」

「田中さんのアカウントは」

「もう、どこにもありません。Entra ID で無効化されて、九個のサービスから消えました。残り三個は岡崎さんが手で消して、Excel の三列も消えました。ファイル名は『残り3つ』のままです。丸嘉のチェックシートは、八十項目のうち七十二項目が『はい』になりました」

「残り八項目は」

「来年の宿題だと、岡崎さんが言っていました。Q1 は、来年の契約書で直すそうです」

　赤海は椅子を回して、モニターに向き直った。

　それから、何も言わずに、からあげ棒を早瀬に差し出した。

　早瀬はそれを受け取って、食べた。

「……おいしいです」

「そうか」

　梨乃は入口でそれを見ていた。早瀬は素直に食べた。自分は食べなかった。田中さんは食べた。たぶん、食べるほうが正しかったのだと、今になって思った。

　あとで聞いたら、赤海は「早瀬さんは素直だ」と言った。褒めているのか呆れているのかは、わからなかった。

---

　梨乃はその夜、ノートの最後のページに書いた。

> 認証は「誰か」。認可は「何ができるか」。ログインできる≠何でも見られる。
> パスワードはハッシュで保存する。ログイン後はセッション番号で本人を追う。
>
> 認証を一か所に寄せる＝IdP。人の正本。商品マスタと同じ構造。
> SSO の本質は「一回でいい」ではなく「パスワードを確かめる場所が一つ」。鍵は一本（社長）。
>
> SAML：IdP が署名した手紙を、ブラウザが三回往復で運ぶ。SP はパスワードを見ない。印鑑と印影。
> OAuth：認可の委任。パスワードを渡さずに、範囲を限った入場券を渡す。認証の規格ではない。
> OIDC：OAuth の上に「名札（id_token）」を足した認証の規格。aud を必ず確かめる。
> SAML と OIDC は同じ仕事の二つの流儀。企業向けは SAML、消費者・API 向けは OIDC。
>
> ゼロトラスト：「壁の内側は信頼する」をやめる。誰が・どの端末で・どこから・何を、を毎回確かめる。
> 製品ではなく設計。壁を、部屋一つ一つの目の前まで下げる。付箋を剥がす。
>
> MDM は二つある。端末のほうと、志村さんのほう。丸嘉が聞いているのは端末のほう。
> （部長の Google はテント用とタープ用。まとめる気配はない）

## 付録　登場した仕組みと用語

| 物語での呼び方 | 正式名称 | 製品例 | 役割 |
|---|---|---|---|
| 誰か | 認証（Authentication） | パスワード、MFA | 本人であることを確かめる |
| 何ができるか | 認可（Authorization） | ロール、GRANT、scope | 確かめた本人に何を許すか。橘さんの「いい」は前例なし |
| 戻せない計算 | パスワードハッシュ | bcrypt, Argon2 | パスワードを平文で保存しない。「全部テント」は短い |
| さっき通った証拠 | セッション / Cookie | — | 認証後、毎回パスワードを送らずに本人を追う |
| 人の正本 | IdP / ディレクトリ | Entra ID, Okta, Google Workspace, JumpCloud | 人の登録と認証を一か所に寄せる |
| 岡崎さんのExcel（残り3つ） | （手作業のID台帳） | Excel | 十二か所を写した台帳。正本ではない。本当の最新にはしない |
| 鍵は一本 | SSO | — | 本質は「認証する場所が一つ」。社長が当てた回 |
| 三回の往復（六回移動） | SAML 2.0 | Entra ID, Okta ⇄ Snowflake, Slack | 署名付きアサーションをブラウザ経由で運ぶ。企業向け |
| 印鑑と印影 | 電子署名と証明書 | X.509 | IdP の秘密鍵で署名、SP は証明書で検証。岡崎さんの得意分野 |
| 入場券 | OAuth 2.0 / access_token | Google, Auth0, Keycloak, Cognito | 認可の委任。scope で範囲、期限あり。認証ではない。落とすと拾った人が入れる |
| 引換券 | 認可コード | — | ブラウザには code だけを通し、サーバー間で token に交換。クリーニングと同じ |
| 会社対会社 | クライアント・クレデンシャル | — | 人がいない API 連携 |
| 名札 | OIDC / id_token（JWT） | Google, Apple, LINE ログイン | 誰が・いつ・誰宛てに認証されたか。aud 検証が必須。読み方は人による |
| 城壁 | 境界防御 / VPN | — | 内側は信頼する設計。在宅・SaaS・乗っ取り端末で破綻 |
| 部屋ごとの門番 | ゼロトラスト | Entra 条件付きアクセス, Cloudflare Access, Zscaler, Okta | 毎回、誰が・端末・場所・操作を検証 |
| 端末の証明書 | 端末管理（MDM：端末のほう） | Intune, Jamf | 会社管理端末であることを門番に示す。志村さんのほうとは別 |
| admin と付箋 | 最小権限 | ロール設計、JIT 権限付与 | 必要な操作だけを、必要なときだけ。yamabiko123 は剥がす |
| 二段階 | MFA | 認証アプリ | 一段階だと部長のアカウントが三つになる |
