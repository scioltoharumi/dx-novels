# 切り替えの夜（上）　痛みを数える

## 第一章　システムを入れたい

「受注管理システムを入れろ」

　七月の経営会議で、大河内はそう言った。理由は三つあった。

　一つ目。丸嘉との連携が始まって二か月、丸嘉からの注文は、丸嘉の担当者がメールで送ってくる CSV を、営業の三上が倉庫にメールで転送し、倉庫の佐藤が倉庫システムに手で入れている。先週、同じ CSV が二回転送され、二十件が二重に出荷された。

「二回転送したのは、俺じゃない」

　三上が言った。

「部長です」

　梨乃が言った。

「……俺か」

「部長です」

　二つ目。法人顧客——山岳会や学校——からの注文は、電話と FAX で来る。営業事務が注文書を Excel に打ち込み、倉庫にメールし、経理の橘が会計システムに請求を手で入れる。先月、FAX の数字の読み間違いで、二十足のはずが二百足の請求書が出た。

　三つ目。EC の注文は自動で倉庫システムに流れるが、EC と丸嘉と法人で、同じ商品の在庫が三つの経路から引き当てられるため、EC で「在庫あり」と出た商品が、実は法人向けに全部押さえられていた、ということが月に数回起きている。

「三つの経路を、一つの受注管理に乗せる。梨乃、これは君がやれ。赤海は忙しい」

「赤海さんは、契約書の件名が『調査』なので、受注管理の導入は範囲外です」

「じゃあ梨乃だ」

「はい」

「システムってのはな」

　梨乃は待った。

「家みたいなもんだ。家は……建てる」

「はい」

「建てる前に、何部屋要るか決めろ」

　社長はそう言った。梨乃は「はい」と答えて、そのあとで気づいた。それは要件定義のことだった。

　梨乃は返事をする前に、一つ聞いた。

「予算と期限は」

「予算は千五百万まで。期限は来年三月。丸嘉の担当者が『御社の注文処理、大丈夫ですか』と言ってきてる。四月から丸嘉の取扱店舗が三倍になる」

---

　その日の午後、梨乃は小部屋に行った。赤海は、Terraform のファイルを開いていた。

「社長が、受注管理システムを入れろと言いました」

「聞いた」

「赤海さんは範囲外だそうです」

「範囲外だ。ただし、相談は範囲内だ」

「相談は、調査の一環ですか」

「調査の一環だ」

「赤海さんなら、何から始めますか」

　赤海は手を止めた。

「『システムを入れろ』は、社長の言葉だ。社長が本当に言いたいのは、『二重出荷と誤請求と在庫の食い違いをなくせ』だ。システムは、そのための手段の一つで、手段は他にもある。まず、今の業務がどうなってるかを、全部書け」

「業務フローですか」

「そうだ。ただし、今ある手順書を写すな。手順書には書いてないことが、現場で起きてる。倉庫と営業事務と経理に、一日ずつ張り付いて、何を、誰が、何分かけて、何件やってるかを数えろ。三つの経路それぞれで」

「一週間かかります」

「一週間で済むなら安い。これを飛ばして要件を書き始めると、半年後に『そんな業務は知らなかった』が出る」

「社長は『何部屋要るか決めろ』と言いました」

「……社長は、たまに当たる」

「半分です」

「半分だ」

「もう一つ、聞いておく。社長は、今のやり方を速くしたいのか。やり方を変えたいのか」

「……違いますか」

「違う。今のやり方を速くするのが改善で、やり方そのものを変えるのが改革だ。FAX を速く打てるようにするのが改善。FAX をやめるのが改革。社長が改善のつもりで、梨乃さんが改革を始めると、三か月後にぶつかる。逆でもぶつかる」

「社長は『三つの経路を一つに乗せる』と言いました」

「なら改革だ。改革のつもりで数えに行け。改善のつもりで数えると、今の手順の中の無駄しか見えない。手順そのものが無駄かどうかは、見えない」

「わかりました」

「あと、数えに行く前に、当たりをつけろ」

「当たり」

「『たぶん、転記が原因だ』と置いてから見に行く。当たりが無いと、見たものを全部メモして、帰ってから溺れる。当たりがあれば、当たりに関係あることだけ数えて、外れたら外れたと書けばいい。外れも記録だ」

「転記、ですか」

「二重出荷は転送、誤請求は読み間違い、在庫の食い違いは引当の場所。三つとも、人が数字を写す場所で起きてる。俺の当たりは転記だ。梨乃さんの当たりは、梨乃さんが立てろ」

　梨乃は、ノートの隅に「当たり：転記」と書いた。自分の当たりも赤海と同じだった。それが良いことなのか悪いことなのかは、わからなかった。

---

　梨乃は、早瀬を連れて、一週間、現場を歩いた。

　月曜の朝、倉庫へ向かう電車の中で、早瀬が言った。

「佐伯さん、これは三現主義ですか」

「……本？」

「本です。現場・現物・現実。手順書ではなく、現場で現物を見る」

「名前は後でいい。まず見よう」

　早瀬は「三現主義（名前は後）」とメモした。梨乃は、それが赤海の言い方に似ていることに、電車を降りてから気づいた。

　月曜は倉庫。佐藤の一日を朝八時から追った。

　EC の注文は倉庫システムに自動で入ってくる。それを佐藤がピッキングリストに印刷し、棚から集め、梱包し、送り状を貼る。丸嘉の CSV は、三上から転送されたメールを佐藤が開き、倉庫システムに一件ずつ手で入れる。四十件で一時間。法人の注文は、営業事務からのメールを見て、これも手で入れる。

「佐藤さん、丸嘉の CSV、二回来たときは、どうやって気づくんですか」

「気づけません。前回は、同じお客さんの名前が二回続いたから、変だと思って三上部長に電話しました」

「部長は何と」

「『俺じゃない』と」

「部長でした」

「部長でした」

　火曜は営業事務。パートの吉田と小川が、FAX と電話の注文を Excel に打ち込む。FAX は一日に十五枚、電話は八本。Excel は「法人受注台帳_2026.xlsx」。打ち込んだら、倉庫と経理に、それぞれ別の形式でメールする。倉庫には商品と数量、経理には金額と請求先。

「二百足の件は」

「FAX の 20 が、手書きで 200 に見えたんです。私が打って、誰も確認しなくて、そのまま経理に行きました」

　吉田は言った。小川が付け足した。

「その FAX、まだ取ってあります。見ますか」

　梨乃は見た。確かに、200 に見えた。20 にも見えた。どちらにも見えた。

「これ、誰が見ても迷いますね」

「迷ったので、電話で確認しようとしたんですが、会長さんが山に登ってて、つながらなくて」

「山に」

「山岳会なので」

　小川の机の引き出しには、「法人受注台帳_2026.xlsx」のほかに、もう一つファイルがあった。「小川用_確認.xlsx」。打ち込んだ注文を、小川が自分のために写して、翌日に倉庫から出荷の連絡が来たかを、手で消し込んでいた。

「これは、手順書にありますか」

「ありません。私が勝手にやってます。前に、メールが倉庫に届いてなくて、三日気づかなかったことがあって」

「勝手に、というのは」

「誰にも言ってません。言うほどのことでもないので」

　梨乃は、それを二枚目のノートに書いた。手順書に無くて、誰にも言っていなくて、無いと三日気づかない仕事。あとで赤海に見せたら、「そういうのを、影の仕事という。一番大事な仕事が、たいてい影にある」と言われた。

　その日の帰り、梨乃は早瀬と、一件の FAX の数字が、どこで何回、人の手で写されるかを数えた。

```
FAX の「20」が通る場所
  1. 営業事務が Excel に打つ            （写す：1回目）
  2. 営業事務が倉庫にメールを書く        （写す：2回目）
  3. 営業事務が経理にメールを書く        （写す：3回目）
  4. 佐藤が倉庫システムに打つ           （写す：4回目）
  5. 橘が会計システムに打つ             （写す：5回目）
  6. 小川が自分の Excel に写す          （写す：6回目・影）

  同じ数字を、六回、人が写す。読むのは、その倍。
```

「六回のうち、一回でも 200 になれば、その先は全部 200 です」

　早瀬が言った。

「そして、六回のうち五回は、写す前の数字を誰も確認しない」

　転記の回数を数えた紙を、梨乃は「転記マップ」と呼ぶことにした。名前があると、社長に見せやすい。

　水曜は経理。橘は、営業事務のメールを見て会計システムに請求を起こす。EC の売上は月末に Snowflake の経理マートから取るが、丸嘉と法人の分は手入力だ。月に百二十件。

「丸嘉の分は、丸嘉からも月末に『支払通知書』が来ます。それと私の入力を突き合わせて、合わないと丸嘉に問い合わせる。先月は八件合いませんでした。会計上、八件は多いです」

「月末は、これが三倍になります。二十五日の締めから月末までは、私は請求しか触っていません。会計上、その一週間は、他の何も頼まないでほしい月です」

　梨乃は「月末×3」と書いた。一週間の観察は、月の第二週だった。第二週に見えるものが月の全部ではない、ということを、橘が先に言ってくれた。

　水曜の夕方、梨乃は一つ、別のことを数えた。法人の FAX が届いてから、靴が倉庫を出るまでの時間だ。

```
法人 FAX 一件の道のり（先週の平均）
  FAX 受信 → 営業事務が打つまで         半日待ち（午後にまとめて打つ）
  打つ                                   6分
  倉庫にメール → 佐藤が開くまで          翌朝まで待ち
  佐藤が打つ                             2分
  引当 → ピッキング → 出荷              その日の午後
  合計                                   約 2.5 日
  うち、人が手を動かしている時間         約 25 分
```

「二日半のうち、二十五分しか働いてない」

　早瀬が言った。

「残りは、待ってる。メールが開かれるのを、打たれるのを、待ってる」

「入力を速くしても、二十五分が二十分になるだけです」

「待ちをなくすと、二日半が半日になる」

　梨乃は、これも二枚目に書いた。速くするなら、手を動かしている時間ではなく、待っている時間のほうだった。

　木曜と金曜は、梨乃と早瀬でフローを描いた。三つの経路を、横に並べた。

```
        EC                    丸嘉                       法人
受注    ECサイト（自動）        メールで CSV（三上が転送）    FAX・電話（営業事務が Excel 入力）
在庫    倉庫システムが引当      佐藤が手入力後に引当           佐藤が手入力後に引当
出荷    倉庫システム            倉庫システム                  倉庫システム
請求    自動（決済代行）        橘が手入力（月末に突合）       橘が手入力
入金    自動                   丸嘉から月末振込               振込を橘が消し込み
```

　そして、数えた。

```
手作業の時間（月）
  佐藤の手入力          丸嘉 40件/日 × 1.5分 + 法人 25件/日 × 2分  ≒ 45時間
  営業事務の入力と転送   FAX・電話 23件/日 × 6分                   ≒ 46時間
  橘の請求入力と突合     120件 × 8分 + 突合 6時間                   ≒ 22時間
  三上の転送と問い合わせ                                          ≒ 8時間
  合計                                                          ≒ 121時間/月

事故（過去6か月）
  二重出荷    3回（計 52件、回収と再発送で約 30万円）
  誤請求      5回（うち1回は 200足、取引先との関係に影響）
  在庫食い違い 月 3〜4回（EC で「在庫あり」→ 実は法人向けに引当済み、キャンセル対応）
```

「三上部長の八時間、というのは」

　早瀬が聞いた。

「転送が一時間。残り七時間は、『俺じゃない』と説明する時間」

「……それ、書いていいんですか」

「書かない。数字だけ書く」

　木曜の午後、梨乃は三人にもう一つ頼んだ。自分の業務を、頻度つきで全部書き出してもらうことだ。毎日、毎週、毎月、毎年。

```
業務一覧（抜粋）
  毎日   FAX・電話受注の入力（営業事務）、丸嘉 CSV の入力（佐藤）、出荷（佐藤）
  毎週   丸嘉への出荷実績報告（三上）、未出荷リストの確認（営業事務）
  毎月   請求入力と突合（橘）、支払通知との照合（橘）、法人への請求書送付（橘）
  毎年   法人顧客の単価改定（三上・営業事務）、年度末の在庫棚卸し（佐藤）
```

「一週間張り付いても、毎月と毎年は見えません」

　早瀬が言った。

「だから、書いてもらう。書いてもらったものにも、抜けはある。本人が『仕事』だと思っていないことは、書かれない」

　抜けは、九月に一つ見つかることになる。

　金曜の夕方、梨乃はこの二枚を赤海に見せた。赤海は三分見て、言った。

「これで、『システムを入れる』が、『月百二十一時間と、半年で八回の事故を、どうするか』に変わった。ここからが、構想だ」

　赤海は、事故の表を指した。

「事故を、種類で分けてある。いい。多い順に並べろ。誤請求が五回、二重出荷が三回、在庫の食い違いは月三、四回だから半年で二十回。上の一つか二つで、事故の大半だ。対策は上から打つ。全部に同じ力で当たるな」

「パレート、ですか」

　早瀬が言った。手は挙げなかったが、挙げかけた。

「名前はどうでもいい。並べろ」

「三上部長の八時間は」

「八時間の中身は、書いてある通りだ。数字は正しい。ただ、部長は声が大きい。声の大きい人の困りごとは、実際より大きく見える。声の小さい人の困りごとは、実際より小さく見える。吉田さんの四十六時間と、部長の八時間を、同じ物差しで並べてあるのは、いい」

「小川さんの影の仕事は」

「数字に入ってないだろう」

「入ってません。月に四時間くらいです」

「入れろ。影の仕事は、システムを入れたあとも影のまま残る。残ると、二重管理になる」

　梨乃は、百二十一時間を百二十五時間に直そうとして、やめた。四時間は「影」として、別の行に書いた。同じ行に足すと、影が影でなくなる気がした。

「部屋の数を、決めるんですね」

「社長の例えを使うな」

「使いません」

　梨乃はノートに書いた。

> 「システムを入れろ」は手段の言葉。目的は、その裏にある痛み。
> 速くするのが改善、やり方を変えるのが改革。どちらの話かを、最初に確かめる。
> 痛みは、現場に張り付いて、数えて、金額にする。手順書を写さない（現場・現物・現実）。
> 数えに行く前に、当たりをつける。外れも記録。
> 数字が人の手で写される場所を数える（転記マップ）。二日半のうち二十五分しか働いていない。減らすのは待ち時間。
> 業務は頻度つきで一覧にする。一週間では毎月と毎年が見えない。影の仕事は、別の行に。
> 事故は種類で分けて多い順に。声の大きい人の困りごとは、大きく見える。
> As-Is（現状）を描くのは、To-Be（あるべき姿）との差を測るため。
> （20 と 200 はどちらにも見える。会長は山にいる。小川さんの Excel は影）

## 第二章　あるべき姿

　八月の第一週、梨乃は「構想」を書き始めた。書き始めて、すぐに止まった。

「赤海さん、あるべき姿、というのが、うまく書けません。『三つの経路が一つのシステムに入る』と書くと、それは結局システムの話で」

「システムの話になるのは、まだ論点が整理できてないからだ。何を解くのか、を先に分けろ」

　赤海はホワイトボードに、三つの問いを書いた。

```
大論点   三つの注文経路の受注業務を、どうすれば事故なく、少ない手間で回せるか

中論点1  注文の「入口」を、どうするか
         ・丸嘉の CSV メールを、システム連携（API）に変えられるか
         ・法人の FAX・電話を、やめられるか。やめられないなら、どう受けるか
中論点2  在庫の「引当」を、どこで一元化するか
         ・三経路の注文が、同じ在庫を、同じ場所で、同じ順番で引き当てる
中論点3  請求と入金を、どう自動化するか
         ・丸嘉の支払通知との突合を、人がやらなくていい形にできるか
中論点4  誰が、いつ、何を確認するか
         ・二重・誤入力を、システムが止めるか、人が止めるか
```

「中論点 1 を見ろ。『法人の FAX をやめられるか』は、システムの話ではない。業務の話だ。山岳会のおじいさんが FAX で注文してくるのを、『これからはウェブで』と言えるかどうかは、三上さんが決める話で、システム屋が決める話ではない」

「業務を変えるか、システムで吸収するか」

「そうだ。FAX をやめられれば、法人の注文は EC と同じ入口に乗る。やめられなければ、FAX を読み取って入力する仕事が残り、その仕事をシステムで支える必要が出る。どちらを選ぶかで、作るものが変わる。だから、システムを決める前に、業務をどこまで変えるかを決める」

　赤海は、ホワイトボードの余白に、もう一つ、縦に五つ書いた。

```
あるべき姿   三経路の注文が、一つの台帳に、人手を介さず入り、同じ在庫から順番に引き当てられる
問題         二重出荷・誤請求・在庫の食い違い。あるべき姿との「差」
課題         入口を一つにする／引当を一か所にする／確認の工程を決める。差を埋めるために「やること」
原因         経路ごとに入口・台帳・引当が別。同じ数字を六回写す
真因         三つの経路を、別々の時期に、別々の人が、別々の理由で作った。誰も全体を持っていない
```

「問題と課題を混ぜるな。問題は差で、課題はやることだ。『二重出荷が起きる』は問題で、『経路を一本にする』は課題だ。混ぜて書くと、構想書が愚痴になる」

「真因は、人がいない、ということですか」

「人がいなかった、ということだ。全体を持つ人が。今日から梨乃さんが持つ。それが真因への対策で、システムは原因への対策だ。真因を放っておくと、システムを入れても、四つ目の経路ができたときに同じことが起きる」

　赤海はさらに、四つの箱を横に並べた。

```
人              プロセス            ルール              システム
「俺じゃない」    転送という工程がある   確認する人が決まって   引当の場所が三つある
                                    いない
```

「二重転送は、人の問題に見える。違う。転送という工程がある限り、誰がやっても、いつか二回送る。プロセスの問題だ。20 と 200 は、確認する人が決まっていない。ルールの問題だ。在庫の食い違いは、システムの問題だ。原因を四つの箱に入れてから、どの箱をどう直すかを決めろ。システムで直せるのは、四つのうち一つだ」

「残りの三つは」

　最初の回は「出す回」だった。三上が言った。

　要件は、三つの層に分けて書いた。赤海の助言だった。

```
業務要件   業務として、何ができなければならないか
           例：丸嘉からの注文を、人手を介さず受注台帳に取り込める
              法人の FAX 注文を入力したあと、営業が承認するまで出荷指示が出ない
              三経路の注文が、同じ在庫から、受注順に引き当てられる

機能要件   システムとして、何を持たなければならないか
           例：丸嘉の発注 API を受け付ける受信口
              受注に「承認待ち」「承認済み」の状態を持ち、承認済みのみ倉庫へ送る
              在庫引当は受注台帳が一元で行い、倉庫システムには出荷指示のみ送る
              受注の重複チェック（同一取引先・同一注文番号は二件目を拒否する）

非機能要件 どのくらい速く、どのくらい止まらず、どのくらい守るか
           例：丸嘉 API は 3 秒以内に応答
              平日 8〜20 時は 99.5% 稼働
              ログインは Entra ID の SSO。ロールは受注・出荷・請求・管理者の四つ
              受注データは 7 年保持
```

「業務要件だけだと、システム屋は何を作ればいいかわからない。機能要件だけだと、業務の人は何のためかわからない。両方書いて、一対一で紐づける。『この機能要件は、この業務要件のためにある』と。紐づかない機能要件は、要望が紛れ込んでる」

　業務要件は、早瀬が一つの型で書き直した。誰が、何のために、何を。そして、どうなったら合格か。

```
業務要件 BR-07
  誰が        営業事務が
  何のために   二重出荷を防ぐために
  何を        同一取引先・同一注文番号の二件目を、登録できない

  合格の条件
    前提   杉並山岳会の注文 No.1234 が登録済みである
    操作   同じ No.1234 を入力して、登録を押す
    結果   「重複」と表示され、登録されない。一件目は変わらない
```

「合格の条件を、今書くんですか」

　三上が聞いた。

「今書きます。三月の受け入れテストで、合格かどうかを判定する条件が、今できます。三月に書くと、間に合わせるために甘くなります」

「前提・操作・結果、というのは」

「本に、Given・When・Then とありました」

　早瀬が言った。赤海は「本でいい」と言った。当たったとは言わなかった。

　早瀬が、紐づけの表を作った。業務要件が十八、機能要件が四十二。紐づかない機能要件が三つ見つかり、三つとも右の枠に移った。

「三つのうち一つが、『受注画面に天気を表示』でした」

「誰が入れたんですか」

「業務要件の一覧を三上部長に見せたときに、鉛筆で書き足されてました」

「鉛筆で」

「消しました」

「……消す」

「受注を消せる人がいると、監査で聞かれます。総務としては」

```
              受注入力  承認    出荷照会  返品    顧客照会  管理
受注          作・読    読・変   読       読      読       読
返品          －        －      －       作・読   －       読

商品          読        読      読       読      －       読
消す          誰も消せない。「取消」の状態にする。取消は管理者だけ
```

```
業務ルール（抜粋）
  経路    承認        単価の時点   返品時の単価   出荷指示
  EC      不要        注文時      注文時        自動
```

「文章で書くと、『法人は承認が要る。ただし……』の『ただし』が五つ並んで、誰も読めなくなる。表にすると、空欄が見える。空欄は、決めていないことだ」

```
1. 目的と範囲（構想書から）
2. 業務フロー（To-Be）　三経路 × 受注・引当・出荷・請求・返品
3. 業務要件一覧（18 件）

10. やらないこと（構想書から。要望一覧を別紙に）
```

　早瀬が言った。

　赤海が言った。

> 誰が何を作り・読み・変え・消すかを表にする。消せる人がいると監査で聞かれる。

> 優先度は、間に合わないとわかる前に決める。Must が八割なら優先度ではない。MoSCoW はロシアではない。
> 決めた版は凍結する。以後は手順で変える。
> 借りるなら、紙の画面は描かない。本物で試す。

## 第四章　作るか、買うか

　十月、梨乃は「何で作るか」を決める段階に入った。選択肢は三つあった。

```
A. スクラッチで内製    高梨と桐山が、要件定義書の通りに一から作る
B. パッケージを導入    受注管理パッケージを買い、足りない部分を作り足す
C. SaaS を契約        クラウドの受注管理サービスを月額で使い、連携部分だけ作る
```

　赤海は、三つを一枚の表にした。

```
                A. 内製              B. パッケージ           C. SaaS
初期費用         人件費のみ            500〜1,500 万           50〜200 万
月額             インフラ 5 万         保守 10 万              利用料 15〜30 万
期間             8〜12 か月            6〜8 か月               3〜5 か月
自由度           何でもできる          カスタマイズ次第         できることが決まっている
5 年後の保守     高梨・桐山がいれば    ベンダーがいれば         SaaS が続いていれば
向く条件         他にない業務          業務が独特              業務が標準的
```

「ヤマビコの受注業務は、独特か」

　赤海が聞いた。梨乃は要件定義書を思い浮かべた。三経路の受注、在庫引当の一元化、承認、返品、請求連携。

「独特ではないと思います。卸と EC と法人を持ってる会社は、たくさんあります」

「なら、C だ。ただし条件がある。SaaS に業務を合わせられるか」

「業務を、SaaS に合わせる」

「A なら、業務に合わせてシステムを作る。C なら、SaaS の決まったやり方に業務を合わせる。SaaS には『受注は承認を通ってから出荷指示』という機能があるだろうが、承認の段階が一つしかないかもしれない。ヤマビコは『営業事務が入力→営業が承認』の一段だから合う。二段必要な会社は、合わない。合わない部分をカスタマイズで足すと、B と同じ値段になり、SaaS の版が上がるたびに壊れる」

「Fit & Gap ですね」

　早瀬が言った。手は挙げなかった。

「……勉強したのか」

「先週、本を読みました。フィットして、ギャップがある。つまり、合ってるところと、隙間があるところを分ける」

　赤海は、少し黙った。

「当たってる」

「当たりましたか」

「本を読んだなら、当たる」

## 付録　登場した型と用語（上）

一からフレームを作らないための型の一覧。「いつ使うか」の列が、型を当てる場面である。

| 物語での呼び方 | 正式名称 | 型の中身・いつ使うか |
|---|---|---|
| 現場に張り付いて数える | 現状業務分析（As-Is） | 手順書でなく実態。件数・時間・金額に落とす。To-Be との差を測るために描く |
| 痛み | 経営課題・業務課題 | 「システムを入れろ」の裏にある目的。手段の言葉を目的に翻訳する |
| 速くするか、変えるか | 業務改善と業務改革（Kaizen と BPR） | 今の流れを速くするのが改善、流れ自体を変えるのが改革。最初にどちらの話かを確かめる |
| 現場・現物・現実 | 3現主義 | 手順書を写さず、現場で現物を見る。名前は後でいい |
| 当たり | 仮説思考 | 数えに行く前に「たぶん転記が原因」と置く。外れも記録する |
| 転記マップ | 転記分析（データフロー図） | 同じ数字を人が何回写すかを数える。写す場所が、誤読と事故の発生源 |
| 二日半のうち二十五分 | リードタイム分析（待ち時間の可視化） | 作業時間と待ち時間を分ける。速くするなら待ち時間のほう |
| 頻度つきの一覧 | 業務棚卸し | 毎日・毎週・毎月・毎年で書き出す。一週間の観察では毎月と毎年が見えない。帳票から逆に引いて検証する |
| 影の仕事 | シャドーワーク（隠れ業務） | 手順書に無く、誰にも言っていない仕事。残すと二重管理になる。別の行に書く |
| 多い順に並べる | パレート分析 | 事故を種類で分け、多い順に。上の一つ二つで大半。対策は上から打つ |
| 声の大きい人 | ヒアリングの偏り | 声の大きい人の困りごとは大きく見える。同じ物差しで並べる |
| 月末×3 | 定常・非定常の分離 | 毎日の流れと月末・年度末を別に書く。第二週に見えるものが月の全部ではない |
| 何を解くのか | 論点設計 | 大論点→中論点。業務の話とシステムの話を分ける |
| 五つの段 | 課題解決の五階層 | あるべき姿→問題→課題→原因→真因。問題は差、課題はやること |
| 四つの箱 | 人・プロセス・ルール・システム | 原因の在処を四つに分ける。システムで直せるのは一つ。残りは業務で直す |
| 空・雨・傘 | 事実・解釈・行動 | 事実と解釈と行動を別の行に。社長は空だけ疑えばいい |
| あるべき姿 | To-Be | 業務の変え方を先に決め、システムはその後 |
| 部屋の数 | 構想書 | 目的・業務の変え方・要求・KPI・体制・予算・やらないこと、効果と費用、前提とリスク、節目、RACI |
| 削減・回避・創出 | 投資対効果（ビジネスケース） | 効果を三つに分け、金額にできるものだけ金額にする。回収期間を書く |
| 節目 | ステージゲート・撤退基準 | 要件定義後・選定後・UAT 後に続ける／やめるを判断。やめる基準を先に書く |
| 誰が決めるか | RACI | 実行・責任・相談・報告。決める人が空欄の仕事が、後で「決めていなかったこと」になる |
| 予備費 | コンティンジェンシー | 想定外のための一〜二割。無いなら無いと書き、決める人を決める |
| 足す前に減らす | ECRS | なくす→まとめる→順番を変える→簡単にする。工程を足すのは、その後 |
| 止めるための承認 | 承認設計（ボトルネックの理論） | 承認は見るためでなく止めるため。全件承認は承認者が一番遅い工程になる |
| 判断・処理・例外 | 業務の三分類 | 処理は機械に、判断は人に、例外は減らすか型にする。月一件の例外は手でやる |
| 前提の表 | 前提条件ログ | 検証していない前提を一覧にし、崩れたときの手を横に書く |
| 影響×関心 | ステークホルダー分析 | 影響が大きくて関心が低い人が後で止める。関心が低いのは、まだ話していないから |
| 起きていないことの表 | リスク登録簿 | 確率×影響×先に打つ手。起きたことの表（課題）と分ける。見立ては誰のものか書く |
| 誰の仕事が変わるか | チェンジ・インパクト分析 | 人の名前で書く。減る人と増える人が見える。増える人に先に話す |
| 件名のルール | クイックウィン | すぐ効く小さな手を先に。消えた痛みはシステムの効果から引く。現場の信用を買う |
| 社長のいる会議 | ステアリングコミッティ | 月次で判断する場。報告の場ではない |
| 出す回と絞る回 | ワークショップ設計（発散と収束） | 目的・出る人・終わったときの姿を先に送る。出す時間と絞る時間を分ける |
| 誰が・なぜ | 要望の出所記録 | 何を・誰が・なぜ。三か月後の「誰が言ったんだ」を防ぐ |
| 右の枠 | 要求管理（要望と要件） | 要件＝ないと目的が達成できない。要望は次の盾 |
| 用事 | ジョブ理論（Jobs to be Done） | 要望の裏の用事を聞く。別の手で満たせることがある |
| 今と同じに | 現行踏襲の禁止 | 理由を聞く。慣れなら教育、相手の都合なら要件。踏襲は無駄ごと固める |
| 誰が・何のために・何を | ユースケース／ユーザーストーリー | 機能でなく目的で書く。合格の条件とセットにする |
| 前提・操作・結果 | 受入基準（Given／When／Then） | 要件定義の時点で UAT の合格条件を書く。後で書くと甘くなる |
| 三層 | 業務要件／機能要件／非機能要件 | 業務と機能を一対一で紐づける。鉛筆も疑う |
| 紐づけ | トレーサビリティ | 業務要件→機能要件→設計→テスト。紐づかないものは要望か漏れ |
| 困るものだけ | 非機能要求グレード | 六項目を全部埋めない。止まると困る時間、同時利用者、月末件数、バックアップ |
| 作る・読む・変える・消す | CRUD 図 | データ×画面で表にする。消せる人がいると監査で聞かれる。「変える」画面が無いデータが見つかる |
| 四つの役割 | 権限マトリクス | 役割×機能。ID のグループと一対一にする |
| 表にする | 業務ルール表（ディシジョンテーブル） | 条件で結果が変わる決めごとは表に。空欄が決めていないこと |
| 落とす順番 | 優先度（MoSCoW） | Must／Should／Could／Won't。間に合わないとわかる前に決める。ロシアではない |
| 八割は優先度ではない | Must の上限 | Must が七〜八割なら一件ずつ聞き直す。「あったほうがいい」が紛れている |
| 凍結 | ベースライン | 合意した版を固定し、以後は変更の手順で変える。凍結しないと変更管理が使えない |
| 紙の画面 | プロトタイプ | 作るなら描く。借りるなら描かず、選定後に本物で試す |
| 作るか買うか借りるか | スクラッチ／パッケージ／SaaS | 業務が標準的なら借り、業務を合わせる |
| 当てる | Fit & Gap | Gap は業務で吸収・連携で作る・諦める。四割超でやめる |
| 薄い紙 | RFI（情報提供依頼） | 厚い紙（RFP）の前に、対応の可否だけ聞いて三社まで絞る |
| 提案依頼 | RFP | 選ぶ基準と重みを先に書いて見せる。デモの進め方と見積の書き方も指定する |
| 重み | 評価表（重み付けスコアリング） | 読む前に決めた重みで採点する。「総合的に判断して」を言わないため |
| 台本 | デモシナリオ | こちらの台本とこちらの実データで、三社同じ流れ。相手の得意画面は見ない |
| 試す | トライアル（PoC） | 契約前に連携と SSO を試す。現場の人にも触らせる（振り返りで反省） |
| 一番苦労したこと | リファレンスチェック | 導入先には「一番苦労したこと」だけ聞く。聞いた答えを自分の見立てで打ち消さない |
| 五年総額 | TCO（総保有コスト） | 初期＋ランニング＋こちら側の手作業。安い提案は手作業を前提にしている |
| 一式 | 見積の内訳 | 作業ごとに人日と単価。内訳が行ごとに分かれていると、後で「内製で」と言える |
| 責任の境目 | 責任分界点 | SaaS 本体／連携／相手側 API／ID。境目の不具合は両側を同席させる |
| 出口 | 出口条項・データの帰属 | 全件出せるか、何日で、どの形式で、作ったものは誰のものか。契約書に書く |
| 出られなくなる | ベンダーロックイン | 独自形式・独自連携が多いほど深い。出口があると出なくて済む |
| 99.5% | SLA の読み方 | 月三時間半止まる。止まったときの手をこちら側で持つ。99.9% に倍を払うかは業務が決める |
| 時間で払う・成果で払う | 準委任／請負 | 融通と保証のトレードオフ。夜座は準委任で「適宜」 |
| 三か月で区切る | 多段階契約 | 導入支援と保守を分ける。固まっていない段階で一年分を約束しない |
