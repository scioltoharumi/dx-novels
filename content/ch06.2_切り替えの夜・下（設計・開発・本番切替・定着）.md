# 切り替えの夜（下）　誰も気づかない夜

## 第五章　設計書は誰のために

　十二月、設計が始まった。

　社C——オーダーリンク社——の担当者は、川辺という三十代の女性で、同じ規模の会社を十社ほど導入してきた人だった。

　川辺は初めて小部屋に来たとき、ノートパソコンと、充電器を四本持っていた。

「四本」

　森田が、廊下でそれを見て言った。

「三本の人がいると聞いたので、一本多く持ってきました」

　森田は、その日から川辺を尊敬した。

「うちの SaaS の設定は、私がやります。ただ、設定の前に『基本設計書』を作ります。画面の項目、帳票の様式、連携の仕様、ロールと権限。これを御社に承認していただいてから、設定に入ります」

「SaaS なのに、設計書がいるんですか」

　早瀬が聞いた。

「SaaS だからこそです」

　川辺は、営業スマイルで言った。営業スマイルなのに、目が笑っていなかった。

「SaaS は、設定項目が三百あります。三百の項目を、御社の業務に合わせてどう設定するかを、設定してから見せると、『思っていたのと違う』が三百回起きます。先に紙で合意します」

「三百回」

「十社で、三千回聞きました」

　赤海が横で言った。

「設計書に書いてないことは、作られない。書いてあることは、書いてある通りに作られる。『当然こうだろう』は、作る側と使う側で違う」

「赤海語録に書きます」

　桐山が言った。川辺が「語録？」と聞き、桐山が「あります」と答え、川辺は「私も語録があります」と言った。「川辺語録」だった。十社分の「思っていたのと違う」が書いてあった。

---

　基本設計書は、五つの章に分かれた。

```
1. 業務フロー（To-Be 詳細）   要件定義の業務フローを、画面と操作の単位まで下ろす
2. 画面設計                   12 画面。各画面の項目、入力規則、ボタンと遷移先
3. 帳票設計                   4 帳票。様式、出力条件
4. 外部連携設計（IF 設計）     6 連携。方向、頻度、形式、項目の対応表、エラー時の扱い
5. データ設計                  受注・受注明細・返品・在庫引当の項目と、xref との紐づけ
```

　梨乃は、画面設計のレビューで、最初の「思っていたのと違う」に出会った。

　法人受注の入力画面。川辺の設計では、顧客を選ぶ欄は「顧客コードを入力」だった。営業事務の吉田が言った。

「山岳会の名前で探せないと、困ります。コードは覚えてません」

「コードは、C-L00034 みたいなものです」

「覚えられません」

「覚えなくていいです」

　川辺は設計書を直した。「顧客名の部分一致で検索し、候補から選ぶ」。ただし、と川辺は付け加えた。

「候補は、xref_customer の法人のみに絞ります。EC の個人会員が候補に出ると、山田太郎さん個人と杉並山岳会を取り違えます。御社が『個人と法人は寄せない』と決めたのは、ここで効きます」

「三上部長は、候補に出ますか」

　早瀬が聞いた。

「三上部長は、個人なので、出ません」

「三つとも」

「三つとも出ません」

「安心しました」

　三上が候補に出たら、営業事務が間違えて三上に靴を売る。それは避けたかった。三上は喜ぶだろうが。

　二つ目は、IF 設計のレビューで出た。倉庫システムへの出荷指示。

```
IF-03 受注台帳 → 倉庫システム（出荷指示）
  方向    受注台帳 → 倉庫
  頻度    承認済み受注が発生するたび（即時）
  形式    倉庫システムの API（JSON）
  項目    受注番号、出荷先、商品コード（倉庫品番）、数量、希望納期
  変換    受注台帳の商品は master_id（P-00512）で持つ
          → xref_product で wms_code（YB00512BK260）に変換して送る
  エラー  倉庫システムが応答しない場合、5 分後に再送。3 回失敗で担当者に通知。
          倉庫が「品番不明」を返した場合、受注を「保留」にし、志村に通知。
```

「エラーの行が、一番長いですね」

　早瀬が言った。

「正常な場合の設計は、誰でも書ける。設計書の価値は、異常な場合に何をするかが書いてあるかどうかで決まる」

　赤海が言った。

「『品番不明』は、志村さんが新商品を正本に登録したが、倉庫への配信が遅れてたときに起きる。志村さんへの通知は、靴紐の話を三十分聞く覚悟で受け取ってほしい」

「通知に、靴紐の欄はありますか」

「ない」

「よかったです」

　高梨が、その行を見て、自分の連携コードの再送処理の設計を直した。#2 のことは、もう言わなかった。

「再送する側を直しただけでは、足りない」

　赤海が言った。

「同じ出荷指示が二回届いても、倉庫の中では一回分にしかならない。その性質が、受ける側に要る。冪等、という。冪等でない相手に再送すると、再送の数だけ二重に出る。倉庫の API が冪等かどうか、ベンダーに聞け。聞き方は『同じ受注番号を二回送ったら、どうなりますか』だ」

　高梨は、その日のうちに倉庫ベンダーに聞いた。答えは「受注番号で弾けます」だった。高梨は IF-03 の「エラー」の行に、「倉庫側は受注番号で二件目を拒否する（ベンダー回答 12/10）」と書き足した。書き足した行が、二月に、少しだけ足りなかったことがわかる。

　三つ目は、データ設計。橘が言った。

「請求は、受注のときの金額ですか、出荷のときの金額ですか。法人は、受注してから出荷まで一週間空くことがあって、その間に値上げがあると、どっちで請求するかで揉めます。会計上、決めておかないと困ります」

　会議室が静かになった。誰も決めていなかった。

　川辺が言った。

「SaaS の標準は、受注時の単価を固定します。出荷時に変えることもできますが、設定で選びます。御社はどちらですか」

　三上と橘が三十分話し、「受注時で固定」に決まった。基本設計書に、一行増えた。

「三十分、何を話してたんですか」

　早瀬が小声で梨乃に聞いた。

「最初の五分で受注時に決まって、残り二十五分は、部長が『じゃあ値上げの前に駆け込みで買われたら』と心配して、橘さんが『それは営業の問題です、会計上は』と答えてました」

「正の字は」

「四画」

「設計書のレビューは、こういう『決めてなかったこと』を見つけるためにある。見つけるたびに、業務オーナーが決める。川辺さんは決めない。私も決めない」

　梨乃は、レビュー記録に書いた。「十二月十二日、請求単価は受注時固定と決定。決定者：三上、橘。所要三十分（うち本題五分）」。

　九月の業務ルール表の空欄が、一つ埋まった。表にしておいたので、空欄が空欄のまま十二月まで来たことが、誰の目にも見えていた。見えていたのに三十分かかったのは、見えていなかったら三月にかかっていた、ということだった。

　データ設計では、佐藤ももう一つ聞いた。

「受注は入ったけど、引当が失敗したら、どうなりますか」

「受注と引当は、一つの単位です」

　川辺が答えた。

「片方だけ残しません。引当に失敗したら、受注も入らなかったことにします。途中で止まったときに、半分だけ残ると、在庫と受注が合わなくなります」

「一つの単位、というのは」

「本では、トランザクション、とありました」

　早瀬が言った。佐藤は「単位」のほうを覚えた。

　岡崎が、最後に聞いた。

「誰が、いつ、承認したかは、後から出せますか」

「出せます。誰が、いつ、何を、どう変えたか。標準で残ります」

「俺のじっくりが、記録されるのか」

　三上が言った。

「記録されます」

「じっくり見た証拠になる」

「なります」

　三上は満足した。監査のための記録が、三上の承認の証拠にもなる。岡崎は「監査ログ」と付箋に書いた。

---

　十二月の第三週、基本設計書のレビューが終わった。指摘は八十七件、そのうち「決めてなかったこと」が二十三件あった。二十三件全部に、決定者の名前が書かれた。

　川辺は言った。

「二十三件は、多いほうです。普通は十件くらいで、残りは設定してから出てきます。設定してから出ると、直すのに三倍かかります」

「なぜ多かったんですか」

「御社が、要件定義の段階で、業務フローを現場で数えていたからです。数えた人が、レビューに出てくる。数えてない会社は、『たぶんこうだと思います』でレビューが通って、後で現場から『違う』が来ます」

　梨乃は、七月の一週間を思い出した。20 と 200 の FAX を。

「あと、御社は、会議で人が本当のことを言います。十社のうち、それができる会社は三社でした」

「三上部長が、ですか」

「三上部長が、一番言います。『俺はデモに弱い』と、初回のデモで本人が言いました。初めてでした」

「詳細設計は」

「SaaS の中の設定は、私が作業手順書として持ちます。御社に見せる必要はありません。御社の連携部分の詳細設計は、高梨さんと桐山さんの中で。基本設計書に書いた IF の仕様が、両者の約束です」

「基本設計書は、今日の版を 1.0 とします。これ以降の変更は、版を上げて、変更の理由を書きます。設定の値も、版と一緒に持ちます。『どの版で合意したか』がわからなくなると、二月に変更要求が来たときに、何からの変更なのかがわからなくなります」

　川辺は、設計書の表紙に「v1.0　2026-12-19　承認：三上・佐藤・橘・志村」と書いた。

　それから、と川辺は続けた。

「一月の設定の前に、画面を三つだけ、先に設定して見せます。法人受注の入力、承認、返品。吉田さんと三上さんと佐藤さんに、本物の画面で触ってもらいます。紙より安くて、三百項目を全部設定するより安い」

「十月に、赤海さんが『借りるなら描くな』と言ってました」

「その通りです。描くのではなく、本物の一部を先に見せます」

　吉田は、一月の第二週に、本物の画面で「杉並」と打った。候補に杉並山岳会が出た。「これなら」と言った。

　川辺は帰り際に、充電器を一本、森田に渡した。

「予備です」

　森田は、それを机の引き出しに入れた。iPhone の充電器の隣だった。

　梨乃はノートに書いた。

> 設計書に書いてないことは、作られない。「当然」は、作る側と使う側で違う。
> 基本設計＝業務・画面・帳票・連携・データ。使う側が読んで承認する。詳細設計は作る側の内部。
> 設計書の価値は、異常時に何をするかが書いてあるかで決まる。
> 再送する側を直すだけでは足りない。受ける側が冪等か（二回届いても一回分か）を聞く。
> 受注と引当は一つの単位。半分だけ残さない。誰がいつ何をしたかは、標準で残す（監査ログ）。
> レビューは「決めていなかったこと」を見つける場。見つけたら業務オーナーが決め、名前を記録する。空欄は表にしておくと見える。
> 設計書には版を付ける。設定の値も版と一緒に。どの版で合意したかが、変更の起点。
> 借りるなら描かない。本物の一部を先に設定して触ってもらう。
> 現場を数えた人がレビューに出ると、設計の段階で「違う」が出る。後で出るより三倍安い。
> （三上部長は候補に出ない。川辺さんは充電器を四本持っている。じっくりは記録される）

## 第六章　動くまで

　一月、開発が始まった。川辺は SaaS の設定を、高梨と桐山は連携の開発を、並行して進めた。

　梨乃は、毎週月曜の朝に三十分、進捗会を開いた。参加者は川辺、高梨、桐山、赤海、早瀬。梨乃は、一枚の表を毎週更新した。

```
WBS（1 月 19 日時点）
  ID    作業                          担当    予定終了   状況        備考
  3.1   SaaS 基本設定（組織・ロール）  川辺    1/16       完了
  3.2   SaaS 画面設定（12 画面）       川辺    1/30       進行 7/12
  3.3   SaaS 帳票設定                  川辺    2/6        未着手
  4.1   丸嘉 API 受信設定              川辺    1/23       完了
  4.2   出荷指示 IF（IF-03）           高梨    1/30       進行      再送処理で設計変更あり
  4.3   会計連携 IF（IF-05）           桐山    2/6        進行
  4.4   xref 連携 IF（IF-01, 02）      桐山    1/23       完了
  4.5   Entra ID SSO 設定             岡崎    1/16       完了
  5.1   データ移行ツール               桐山    2/13       未着手
```

　最初の進捗会で、赤海が表を見て聞いた。

「この表で、一日遅れたら三月二十八日が一日遅れる作業は、どれだ」

　梨乃は、矢印を辿った。4.2 の出荷指示が終わらないと 6.1 の結合テストが始まらない。結合テストが終わらないと UAT が始まらない。UAT が終わらないとリハーサルができない。

「4.2、6.1、6.2、7.1、7.2 です。それと、丸嘉の API の切替日程。丸嘉は、こちらで動かせません」

「その列に、予備を置け。全部の作業に予備を置くな。予備を全部に置くと、全部が予備を使い切る。余裕があると、着手が遅れる。人はそういうふうにできてる」

「学生症候群、と本にありました」

　早瀬が言った。

「夏休みの宿題だ」

　赤海が言い、高梨が小さく頷いた。

　梨乃は、高梨に 4.2 の残りを、三つの数字で聞いた。うまくいったら何日、たぶん何日、悪ければ何日。高梨は「三日、五日、十日」と答えた。梨乃は、表には十日で置いた。

「十日は、悲観しすぎでは」

「悲観の数字で置いておくと、五日で終わったときに五日空く。楽観で置くと、十日かかったときに七日足りない。空くほうがいい」

　梨乃はもう二枚、表を作った。一枚は、いま起きている困りごとの表。もう一枚は、八月に作った、まだ起きていない困りごとの表。八月の表の「倉庫システムのテスト環境が使えない」は、一月に起きた。起きた行は、一枚目に移した。

```
課題（起きている）
  ID    内容                                担当    期限    状態
  I-03  倉庫テスト環境が週 2 日しか使えない    梨乃    1/23    ベンダーと交渉中
  I-04  「処理中」応答の扱いが未定             高梨    1/30    倉庫ベンダーに確認中

リスク（まだ起きていない）
  丸嘉の切替日程が 4/6 より遅れる          中   中   3 月第一週に丸嘉と日程を固める
  UAT 期間に月末が重なり橘が出られない      高   中   UAT を 3/9〜13 に置き、締めを避ける
```

　誰に、いつ、何を伝えるかも、一枚にした。

```
伝え方の表
  週次    月曜 9:00   進捗会 30 分            川辺・高梨・桐山・赤海・早瀬     一枚の表
  月次    第一金曜    ステアリングコミッティ   社長・業務オーナー              判断が要ること。信号の色つき
  隔週    水曜        「今どこまで」一枚       吉田・小川・佐藤・橘・志村       できたこと、次に頼むこと
  都度    －          丸嘉                    担当者                          切替日程と API の件だけ
  一回    3 月        会長への手紙             三上が書く                       「いつも通り FAX で」
```

「隔週の一枚は、要りますか」

　早瀬が聞いた。

「要る。吉田さんと小川さんは、八月に『午後の二時間』で関心を持った。関心は、放っておくと二か月で消える。何も伝えないと、『何か決まったらしい』になる」

　一月の第三週、高梨が言った。

「4.2 は、九割できてます」

　梨乃は、赤海の顔を見た。赤海は何も言わなかった。からあげ棒が、〇度だった。

　翌週、高梨は同じことを言った。

「九割です」

　からあげ棒が、マイナス五度に下がった。初めて見る角度だった。

　その週の会の後、赤海は梨乃に言った。

「『九割』が二週続いたら、それは五割だ。残りの一割に、まだ見えてない問題がある。高梨さんに、『何が残ってるか』を、作業の名前で聞け。割合で聞くな」

「高梨さんは、嘘をついてるわけじゃないですよね」

「ついてない。九割だと本当に思ってる。残りの一割が、一割に見えるだけだ。#2 に頑張れと言ってたときと同じで、高梨さんは、自分の作ったものを、少し楽観的に見る」

　梨乃は高梨に聞いた。

「4.2 で、残ってる作業を、名前で教えてください」

　高梨は、残っている作業を三つ挙げた。

　倉庫システムの API が、まれに「処理中」という返事を返し、それを成功とも失敗とも扱えないこと。再送のたびに倉庫に同じ出荷指示が二重に入る可能性があること。そして、倉庫システムのテスト環境が、ベンダーの都合で週に二日しか使えないこと。

「三つ目は、高梨さんの問題ではありません」

「……そうですか」

「週に二日しか試せなければ、誰でも遅れます」

　梨乃はその日のうちに、倉庫システムのベンダーに電話し、二月中はテスト環境を毎日使えるように交渉した。追加費用は五万円だった。

「進捗会の仕事は、遅れを責めることではなく、遅れの原因のうち、担当者が自分で解決できないものを、代わりに解決することだ」

　赤海は言った。からあげ棒が、〇度に戻った。

「あと、『九割』と言われたときに、俺の棒がマイナスになったのは、記録しなくていい」

「もう書きました」

「……そうか」

---

　二月の第一週、三上が梨乃の席に来た。

「受注画面に、やっぱり購入履歴を出せないか。営業事務が、『前回も同じ数量でしたか』と聞かれて、Excel を開き直してる」

　梨乃は、要件定義書の別紙「要望一覧」を開いた。一番上に「受注画面に天気を表示」とあり、二番目に「受注画面に購入履歴を表示」とあった。

「三上さん、これは変更要求です。手順があります」

「天気は」

「天気は、手順に乗せません」

「乗せてくれ」

「乗せません」

```
変更要求 CR-004
  内容      受注画面に、同一顧客の直近 5 件の受注を表示する
  要求者    三上
```

```
4. 伝える             隔週の「今どこまで」一枚。会長への FAX
5. 障害を除く          倉庫のテスト環境、五万円
6. 短い期間で成果       九月の件名のルールで二重転送ゼロ。三月三十日、誰も気づかない月曜
7. 定着               ハイパーケア、運用設計、旧 Excel を開いた回数ゼロ
8. 文化               まだ。次を早瀬がやるなら、そのとき
```

「順番を飛ばすと、戻る、と本にありました」

「飛ばしてない」

　赤海が言った。

「飛ばしていないのは、順番を知っていたからじゃない。一つずつ、困ったことに手を打ったら、この順番になった。本は、後から読むと当たってる」

「当たりましたか」

「本が当たった」

　早瀬は「八段階（本が当たった）」とメモした。

「佐藤さんの『請求書に載らなかった』は、悪かったことなんですか」

　早瀬が聞いた。

「載るべきだと思ってます」

　佐藤が言った。

「赤海さんの仕事が、二年間、請求書に載ってない。倉庫としては、そういうのは、あとで揉めるので」

「調査の一環なので」

「調査、長すぎます」

　小部屋が静かになった。岡崎が、少しだけ目を伏せた。赤海は、からあげ棒を齧った。何も言わなかった。

　会の最後に、大河内が言った。

「次は、倉庫システムのクラウド版への移行だ。梨乃、これは早瀬にやらせろ。梨乃は横で見ろ」

　早瀬は、顔を上げた。

「僕が、ですか」

「二年前、梨乃も同じ顔をした」

　赤海が、隅で言った。

「あと、佐藤の件は、俺が岡崎と話す」

　大河内は、それだけ言って、出ていった。岡崎が、初めて、少し嬉しそうな顔をした。

## 終章　一枚目の図

　六月、早瀬は倉庫システム移行の構想書を書き始めた。書き始めて、すぐに止まった。梨乃の席に来て、言った。

「佐伯さん、あるべき姿、というのが、うまく書けません」

　梨乃は、二年前の自分を思い出して、少し笑った。

「論点を分けて。何を解くのか。業務の話と、システムの話を、分けて」

「それ、赤海語録にありますか」

「たぶん、ある。私が言われたのが最初だと思う」

「じゃあ、梨乃語録です」

「やめて」

　早瀬は小部屋に行き、ホワイトボードに三つの問いを書き始めた。赤海は Terraform のファイルを開いたまま、振り向かなかった。からあげ棒は、〇度だった。まだ、何も始まっていない角度だった。

　早瀬が小部屋に行く前に、梨乃はノートの一枚を破って渡していた。一年かけて書いた、軸の一覧だった。

```
軸（先に置いてから、枠に入れて議論する）
  改善／改革                       速くするのか、変えるのか
  As-Is／To-Be／差                 現状、あるべき姿、その差
  業務／システム                   どちらの話か
  あるべき姿／問題／課題／原因／真因   問題は差、課題はやること
  人／プロセス／ルール／システム      原因の在処。システムで直せるのは一つ
  空／雨／傘                       事実、解釈、行動
  判断／処理／例外                 消えるのは処理
  要望／要件                       あると嬉しい、ないと困る
  業務要件／機能要件／非機能要件
  Must／Should／Could／Won't
  作る／買う／借りる
  Fit／Gap（吸収・作る・諦める）
  準委任／請負                     時間か、成果か
  一発／並行／段階                 戻せる形か
  正常／異常／端の値
  影響×関心                       誰が後で止めるか
  確率×影響                       起きていないことの表
  削減／回避／創出                 効果の分け方
  知らない／できない／やりたくない／得がない   使われない理由
  指揮／対応／連絡／記録           当日の四役
```

「一から枠を作らなくていい。軸を先に置いて、枠に入れて、話す。枠に入らないものが出てきたら、枠を壊せばいい。壊すためにも、先に枠が要る」

「これ、赤海語録ですか」

「半分は本。半分は、私が書いた。名前は、どうでもいい」

　早瀬は、紙を折って、ノートに挟んだ。

　梨乃は、自分のノートを開いた。最初のページに、二年前の九月、こう書いてある。

> 業務システムのデータベースは、業務を動かすためのもの。
> 集計のために使うと、業務のほうが止まる。
> （部長のテントが止まる。部長の家のテントの数は不明）

　最後のページに、梨乃は書いた。

> 「システムを入れろ」は手段の言葉。痛みを、現場で数えて、金額にする。20 と 200 はどちらにも見える。
> 構想＝目的、業務の変え方、指標、体制、予算、やらないこと。業務を先に決める。部屋の数を決める（社長）。
> 要望と要件を分ける。三層で書き、紐づける。増えたら記録する。優先度は先に決める。天気は右の枠。
> 作るか買うか借りるか。借りるなら業務を合わせる。基準を先に書く。部長はデモに弱い。
> 設計書に書いてないことは作られない。異常時が価値。決めていないことを見つけて、決める人を記録する。
> 進捗は作業の名前で。変更は手順で。テストは異常系まで。UAT の基準は先に。九割は五割。
> 切替は戻せる形で。リハーサルは二回。判定は表で。印鑑の欄。成功の姿は「誰も気づかない」。
> 定着＝運用設計、効果測定、振り返り。プロジェクトは終わるが、システムは終わらない。
> 使われない理由は四つ。教育で直るのは一つ。下がってから上がる。旧い手段が残っている回数を数える。
> 型は、一から作らない。軸を先に置いて、枠に入れて、話す。枠に入らなければ、壊す。
>
> 二年前、一枚目の図を描いたとき、六枚目は見えていなかった。
> ただ、一枚目に「集計に使うな」と書いたから、二枚目が要った。
> 二枚目の正本が割れていたから、三枚目の人の正本が要った。
> 三枚目で壁をなくしたから、四枚目の門番が要った。
> 四枚目で一台では足りないとわかったから、五枚目の家畜が要った。
> 五枚全部があったから、六枚目は、作れた。
>
> 一枚ずつでいい。ただし、一枚目に、本当のことを書く。
> （テントの数は、まだ不明。調査は、まだ続いている。佐藤さんは載せたがっている）

## 付録　登場した型と用語（下）

上巻の付録の続き。「型の中身・いつ使うか」の列が、型を当てる場面である。

| 物語での呼び方 | 正式名称 | 型の中身・いつ使うか |
|---|---|---|
| 紙で合意 | 基本設計（外部設計） | 業務・画面・帳票・IF・データ。使う側が承認する。設定してから見せると「思っていたのと違う」が三百回 |
| 作る側の内部 | 詳細設計 | 基本設計の IF 仕様が両者の約束 |
| エラーの行 | 異常系設計 | 設計書の価値は異常時に何をするかで決まる。端の値も設計書に書く |
| 二回届いても一回分 | 冪等性 | 再送する側を直すだけでは足りない。受ける側に「同じ番号を二回送ったらどうなるか」を聞く |
| 一つの単位 | トランザクション整合性 | 受注と引当は片方だけ残さない。半分残ると在庫と受注が合わない |
| じっくりの記録 | 監査ログ | 誰が・いつ・何を・どう変えたか。監査のための記録が承認の証拠にもなる |
| 決めていなかったこと | 設計レビュー | 見つけて、業務オーナーが決め、名前を記録。空欄は表にしておくと見える |
| 版 | 設計の版管理（構成管理） | 設計書と設定値に版を付ける。どの版で合意したかが変更の起点 |
| 本物の一部 | プロトタイプ（設定型） | 借りるなら描かず、三画面だけ先に設定して触ってもらう |
| 「当然」の違い | 暗黙の前提 | 作る側と使う側の当然は違う。書いてないことは作られない |
| 一枚の表 | WBS／進捗管理 | 作業の名前で聞く。「九割」が二週続いたら五割 |
| 一日遅れたら | クリティカルパス | 一日遅れると期限が一日遅れる作業の列。外部の日程も含める。予備はここに置く |
| 三つの数字 | 三点見積 | 楽観・最頻・悲観。表には悲観で置く。空くほうがいい |
| 予備の置き場 | バッファ管理（学生症候群） | 全部に予備を置くと全部使い切る。余裕があると着手が遅れる |
| 起きている表・起きていない表 | 課題管理・リスク管理 | 二枚に分ける。起きたら移す |
| 伝え方の表 | コミュニケーション計画 | 誰に・いつ・何を・どの手段で。関心は放っておくと二か月で消える |
| 手順を通す | 変更管理（CR） | 影響を見て、決める場で決める。直接頼むと五回で破綻する |
| 四段階 | 単体／結合／システム／UAT | 異常系まで。作った人、PMO、業務の人と、試す人が変わる |
| 端の値 | 境界値テスト | 0・マイナス・999・全角。端が設計書に無いと作る側が端を決める |
| 一本の流れ | シナリオテスト | 受注から請求まで業務を一巡させる。機能単位で合格しても通しで落ちる |
| 直すと隣が壊れる | 回帰テスト | 直すたびに全部流す。全部流せる本数（十五本）にしておく |
| 月末の三倍 | 性能テスト | 非機能に書いた件数で、月末が来る前に流す |
| 連携は一発、画面は小さく | ハイブリッド開発 | 仕様が決まっている部分は一発、触らないと違いが出ない部分は反復 |
| 不具合の表 | 不具合管理 | 発見・原因・対策・担当・期限・状態。同じ画面に集まれば設計の問題 |
| 合格の条件 | UAT 合格基準 | 始める前に決める。致命ゼロ、重大は回避策つきで三件以下 |
| 部屋ごとに運ぶ | 移行方式（段階切替） | 一発・並行・段階。経路ごとに切り替え、その経路だけ戻す |
| 戻す基準 | ロールバック計画 | 何が起きたら、誰が、いつまでに判断し、どう戻すか |
| 止める時間 | 業務凍結（フリーズ） | 旧業務への入力を止める時間と、その間に来た注文の行き先 |
| 分で書く | 切替手順書（タイムライン） | 何時に誰が何をするか。件数と金額の照合を手順に入れる |
| 四役 | 切替当日の体制 | 指揮・対応・連絡・記録。指揮は手を動かさない |
| 二回やる | 移行リハーサル | 一回目で壊れる場所を知り、二回目で直したことを確かめる |
| 変換の表 | データ移行の変換ルール | 略称→正式名、廃番→廃番コード。手で直さず表で直す。本番でも同じ結果になる |
| 件数と金額 | 移行データ検証 | 件数が合っても金額は合わないことがある。両方照らす |
| 表で判定 | カットオーバー判定 | 項目と基準を先に決める。印鑑の欄を足す |
| 何も変わりません | 切替の周知 | 影響が大きくて関心が低い人に、先に「何も変わらない」と言う |
| 書けなくする | 旧手段の停止 | 旧 Excel は残したまま読み取り専用に。残すと使う |
| 二時間以内 | 回避策の体制（ハイパーケア前夜） | 本番で初めて起きることは必ずある。回避策を立てる時間と人を先に決める |
| 二週間 | ハイパーケア | 切替直後の即日対応期間。三週目で減らなければ設計か教育の問題 |
| 下がってから上がる | 変化曲線 | 二週目に一度、前より遅くなる。先に伝える。戻すと二度と追い越さない |
| 四つの理由 | 抵抗の四類型 | 知らない・できない・やりたくない・得がない。教育で直るのは一つ |
| 五つの順番 | ADKAR | 認知→欲求→知識→能力→強化。知識だけ教えて本番にすると覚えない |
| 三回 | 教育計画 | 説明会→ハンズオン→本番直前の再確認。三回目は覚えたかを確かめる回 |
| 質問と答え | FAQ | ハイパーケアの問い合わせを一覧にして一番上に貼る。同じ質問が来なくなる |
| 開いた回数 | 定着度の測定 | 新システムの利用率より、旧い手段が残っている回数のほうが正直 |
| 念のための Excel | 抜け道の封鎖 | 「念のため」は使われる。残すなら書けなくする |
| 三週間ゼロ | 短期成果の見える化（経営者のメッセージ） | 効いたことを経営者が自分の口で、早く、具体的に言う |
| 先に覚えた人 | キーユーザー | 部署ごとに一人。窓口の前にもう一段置く |
| 終わったあと | 運用設計 | 窓口・マスタ・不具合・変更・版上げ・監視・棚卸し・手順書の更新・つなぎの片づけ・効果の測定 |
| つなぎの片づけ | 技術的負債の管理 | 急いで作ったものは、いつ消すかを今書く。残すと二重管理 |
| 手順書の直す人 | 業務標準の維持 | 更新されない手順書は半年で嘘になる。直す人と直した日を書く |
| 半年測る | ベネフィット実現管理 | 効果はプロジェクトの後に出る。測る人と時期を先に決める |
| 体温 | 効果測定（KPI） | 構想書の指標に対して報告。回収期間を実績で計算し直す |
| 良かった・悪かった・次 | 振り返り（レトロスペクティブ） | 個人を責めない。自分の見立てで打ち消したことも挙げる |
| 八つの段 | Kotter の変革八段階 | 危機感→推進→姿→伝える→障害除去→短期成果→定着→文化。本は後から読むと当たっている |
| 軸の一覧 | 整理軸 | 一から枠を作らない。軸を先に置いて、枠に入れて話す。入らなければ壊す |
