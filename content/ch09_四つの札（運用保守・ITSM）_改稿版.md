# 四つの札（改稿版）

## 第一章　三日間の沈黙

　二月の第二週、木曜の朝、橘が小部屋に来た。眼鏡は上がっていた。戦闘態勢のほうだった。

「会計に、受注システムからの請求データが、三日分、届いてません。会計上、三日は長いです」

　赤海がログを見た。

　月曜の深夜、受注 SaaS の社C——オーダーリンク——が版を上げていた。版上げで、連携の項目名が一つ変わっていた。桐山が作った会計連携は、その項目を読めず、月曜の夜からエラーで止まっていた。

「アラームは」

「#alerts に、月曜の深夜二時に一件、出てます」

　早瀬が Slack を開いた。#alerts には、月曜の深夜、一行の通知があった。その下に、火曜の朝、高梨が「見ます」と書いていた。その下には、何もなかった。

　高梨は、火曜の朝、通知を見て、「見ます」と書き、その直後に丸嘉の API の別の問い合わせが来て、そちらを対応し、そのまま忘れていた。水曜は高梨の休みだった。当番は桐山に代わっていたが、桐山は「高梨さんが見ますと書いたから」と、見なかった。

「見ます、と書いたのは、覚えてます」

　高梨が言った。

「見なかったのも、覚えてます」

「……#2 のときは、忘れなかったのに」

「#2 は、名前があったからです。連携には名前がない」

「IF-05 という名前がある」

「IF-05 は、名前というより、番号です」

「誰も悪くない」

　赤海は言った。それは、この小部屋で何度も言われた言葉だった。だが、今回は、少し違った。

「誰も悪くないが、三日、止まってた。三日は、長い」

「会計上も長いです」

　相殺後、十二。

---

　その日の午後、梨乃は、過去一か月の Slack を調べた。ヤマビコグループには、システムに関する連絡が流れる場所が、九つあった。

```
#alerts            監視の自動通知。人間の会話はほとんどない
#oms-support       受注システムの問い合わせ。早瀬が一次対応
#ssc-finance       SSC への問い合わせ。橘のチーム。佐藤社長の「請求書は」が三十件
#it-helpdesk       パソコン・アカウントの問い合わせ。岡崎
#ec-dev            高梨と桐山の開発の話。ここに障害の話も混ざる
#warehouse         倉庫の業務連絡。倉庫システムの不具合もここに書かれる
#rise-factory      ライズの工場。生産管理の問い合わせは真田さんに直接メール
赤海への DM         何でも。「今、買っていいか」も
高梨への DM         何でも。「ストア重くないか」も
```

　一か月で、システムに関する問い合わせと障害の連絡は、二百十四件あった。うち、九つの場所のどこにも書かれず、口頭か DM で処理されたものが、推定で六十件。二百十四件のうち、「誰が対応して、いつ終わったか」が記録に残っているものは、九十件だった。

「三上部長の分は」

　早瀬が聞いた。

「『今、買っていいか』が十四件、『ストア重くないか』が九件。合わせて二十三件。全部、システムの問い合わせに分類した」

「分類していいんですか」

「システムに関する問い合わせだ。答えは全部『だめです』か『重くないです』だが」

「半分以上が、どこかに消えてる」

「消えてない。誰かの頭の中で処理されてる。志村さんの台帳と同じだ」

　赤海は、ホワイトボードに向かった。

「三年間、俺たちは、作ることばかりやってきた。受注システムのときに運用設計を書いたが、あれは受注システム一つの話だ。八つのシステムと、十一本の連携と、三社と、百二十人の運用は、誰も設計してない」

```
作る（Build）    要件を決め、設計し、開発し、テストし、切り替える。プロジェクト。終わりがある
運用する（Run）  動いているものを、動き続けさせる。問い合わせに答え、壊れたら直し、変える。終わりがない
```

「Build には、手順ができた。Run には、まだない。今日の三日間は、Run の手順がないことの、最初の請求書だ」

「請求書」

　佐藤が、Slack に書いた。#ssc-finance だった。誰も返事をしなかった。

---

　その日の夕方、廊下で社長に捕まった。

「三日止まってたと聞いたぞ」

「はい。運用の仕組みがなかったので」

「運用ってのはな」

　梨乃は待った。

「家は、建てたら掃除だ」

「はい」

「掃除は、終わらない」

「……はい」

「建てた奴は、掃除しない」

　社長は歩いていった。梨乃は「掃除（社長）」と書いた。三つ言って、三つとも当たっていた。今日は、当たる日だった。

　梨乃はノートに書いた。

> 作ることには終わりがある。運用には終わりがない。家は建てたら掃除（社長・三連続）。
> 問い合わせと障害の連絡が九か所に散り、半分は記録に残らない。部長の二十三件も含む。
> アラームは出ていた。「見ます」と書いて、誰も見なかった。通知があることと、対応が終わることは別。
> 三年、作ることばかりやってきた。運用は、誰も設計していなかった。建てた奴は掃除しない。

---

## 第二章　四つの札

　翌週、赤海は、二百十四件の連絡を、四つに分けた。

```
1. サービス要求   壊れていない。何かをしてほしい
                 「新入社員のアカウントを作って」「Power BI に営業マートの権限をつけて」
                 「受注画面に項目を足せないか」（これは変更要求へ）
                 「今、買っていいか」（部長）
                 → 132 件

2. インシデント   壊れている。今、業務が止まっているか、止まりそう
                 「会計連携が止まっている」「倉庫のハンディが繋がらない」「丸嘉 API が遅い」
                 「ストア重くないか」（部長。九件中九件、重くなかった）
                 → 41 件

3. 問題          インシデントの原因。同じインシデントが繰り返す理由
                 「会計連携が、SaaS の版上げのたびに止まる」（今回で 3 回目）
                 「ハンディが月に 2 回繋がらなくなる」
                 → インシデント 41 件のうち、繰り返しているもの 4 種類

4. 変更          何かを変える。変えると、インシデントが起きることがある
                 「社C の版上げ」「Terraform の apply」「新しい SaaS の追加」
                 → 28 件。うち 6 件が、変更の直後にインシデントを起こしている
```

「この四つを、四つの札と呼ぶ。問い合わせが来たら、まず、どの札を貼るかを決める。札が違うと、やることが違う」

「札！」

　三上が、入口にいた。

「強い」

「強くないです」

「四つの札。麻雀か」

「麻雀ではないです」

「五つ目は」

「ありません」

「天気は」

「札ではないです」

　三上は「わかった」と言った。天気を諦めた声だった。二回目だった。

```
サービス要求   手順通りにやる。急がない。記録して、終わったら閉じる
インシデント   まず業務を戻す。原因は後。時間を測る
問題          原因を突き止める。急がなくていいが、終わらせる
変更          事前に影響を見て、承認して、記録して、やる。失敗したら戻す
```

「今回の三日間は、インシデントの札が貼られなかった。#alerts に通知が出て、高梨さんが『見ます』と書いた。それは、札が貼られてない状態だ。札が貼られてれば、『誰が、いつまでに、業務を戻すか』が決まり、決まってないことが見える」

　早瀬が聞いた。

「札を貼るのは、誰ですか」

「一つの窓口だ」

「わかりました！　岡崎さんですね！」

　赤海が止まった。

「……当たってる」

「当たりましたか！」

「岡崎さんは、いつも、何かの正本だ。窓口の正本も、岡崎さんになる」

　早瀬は「窓口＝岡崎さん（当たった・人）」と書いた。人で当たったのは、初めてだった。

---

　赤海は、九つの場所を、一つにする図を描いた。

```
                  ┌──────────────────────────┐
  社員 120 人 ──▶  │  サービスデスク（一つの窓口）  │ ──▶ 札を貼る ──▶ チケット
  丸嘉・取引先 ─▶  │  Slack #helpdesk / メール    │
  監視の通知 ───▶  │  / 電話                      │
                  └──────────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          一次対応         二次対応          ベンダー
          （岡崎＋1名）    （早瀬・高梨・     （社C 川辺、WMS、
          手順で解決      桐山・橘チーム）    社F 真田、AWS）
```

「サービスデスク。全部の問い合わせと、全部の監視通知が、ここに来る。ここで札を貼り、チケットにする。チケットは、番号と、札と、担当と、期限と、状態を持つ。閉じるまで、消えない」

「今の九つの Slack は」

「残していい。ただし、九つのどこに書かれても、サービスデスクがそれを拾ってチケットにする。最終的には、#helpdesk 一つに寄せる。岡崎さんが十二個のサービスを Entra ID に寄せたのと同じだ。窓口の正本を一つにする」

　岡崎が、その会議に来ていた。

「私が、窓口ですか」

「岡崎さんは、もう窓口です。#it-helpdesk で、パソコンとアカウントの問い合わせを、六年やってる。それを、システム全部に広げる。ただし一人では無理なので、もう一人雇う。それと、道具を入れる」

```
サービスデスクの道具（ITSM ツール）
  Jira Service Management / Freshservice / Zendesk / ServiceNow
  チケット、札（分類）、優先度、担当、期限、状態、ナレッジ、SLA の計測
  Slack やメールから自動でチケットを作る
  監視の通知（#alerts）から自動でインシデントのチケットを作る
```

「#alerts の通知が、自動でインシデントのチケットになる。チケットは、担当が決まって、閉じるまで消えない。『見ます』と書いて忘れることが、できなくなる」

　高梨が、少し安心した顔をした。

「僕、もう『見ます』と書きません」

「書いていい。書いたら、チケットの状態が『対応中』に変わる。変わったものは、消えない」

「消えない」

「#2 と同じだ。増えはしないが、消えない」

　岡崎が言った。

「もう一人、というのは」

「コールセンターの経験がある人がいい。問い合わせを受けて、分類して、記録する、が身についてる人」

「心当たりがあります」

「誰ですか」

「甥です。コールセンターの管理者を八年やってて、今、転職を考えてます」

「甥」

「西村と言います。私とは苗字が違います」

　岡崎の世界観には、正本の他に、甥もあった。

　梨乃はノートに書いた。

> 四つの札。サービス要求（壊れていない）、インシデント（壊れている）、問題（繰り返す原因）、変更（変える）。麻雀ではない。五つ目はない。
> 札が違うと、やることが違う。インシデントは、まず業務を戻す。原因は後。
> 一つの窓口。全部の問い合わせと通知が来て、札を貼り、チケットにする。チケットは閉じるまで消えない。#2 と同じ。
> 窓口の正本を一つにする。岡崎さん（早瀬・人で当たった）。
> （岡崎さんには甥がいる）

---

## 第三章　優先度と約束

　三月、ITSM ツールが入り、岡崎と、新しく雇った西村がサービスデスクになった。

　西村は三十代で、前職はコールセンターの管理者だった。初日、小部屋に来て、赤海に挨拶した。

「お問い合わせありがとうございます。西村です」

「……問い合わせてない」

「すみません、癖で。八年やると、最初の一言が出ます」

「治せるか」

「治りません。前職でも、家族に言ってました」

　西村は、それ以降も、小部屋に入るたびに「お問い合わせありがとうございます」と言った。三日で、誰も気にしなくなった。

　最初の週、西村が言った。

「チケットが、一日に十五件来ます。全部、『急ぎ』と書いてあります」

「全部？」

「全部です。あと、三上部長からの『今、買っていいか』が、チケットになってます。一日二件」

「それは、サービス要求だ」

「サービス要求で、優先度は」

「一番低い」

「『急ぎ』と書いてありますが」

「部長は、いつも急ぎだ」

　赤海は、二つの軸を書いた。

```
影響度   何人の、どの業務が止まるか
         高：丸嘉・お客さん・全社に影響　　中：一部門　　低：一人

緊急度   今すぐでないと、どうなるか
         高：今、止まっている　　中：今日中　　低：来週でも困らない

優先度 ＝ 影響度 × 緊急度
              緊急・高    緊急・中    緊急・低
  影響・高      P1         P2         P3
  影響・中      P2         P3         P4
  影響・低      P3         P4         P4
```

「『急ぎ』は、緊急度の話だ。優先度は、それに影響度を掛ける。三上部長の『今すぐ、自分の Power BI が開かない』は、緊急・高、影響・低で、P3 だ。丸嘉の『API が三秒かかる』は、緊急・中、影響・高で、P2 だ。三上部長より、丸嘉が先」

「『今、買っていいか』は」

「緊急・低、影響・低。P4 だ。表の一番右下」

「三上部長に、そう言えますか」

「言うのは、西村さんじゃない。この表が言う。表は、ステアリングコミッティで社長が承認する。三上部長が『なぜ俺が後だ』と言ったら、『社長が承認した表で P4 です』と言う」

　三上が、入口にいた。

「なぜ俺が後だ」

「社長が承認した表で P4 です」

「まだ承認してないだろう」

「来週、承認されます」

「……わかった」

　三上は、初めて、「わかった」に感嘆符をつけなかった。P4 が効いた。

　その週、ステアリングコミッティで表が承認された。大河内は表を見て、「俺は、どこだ」と聞いた。梨乃が「社長は、体温を聞くだけなので、チケットになりません」と答えた。大河内は「そうか」と言った。少し残念そうだった。

---

　次に、約束を決めた。

```
SLA（サービスデスク）
  優先度   一次応答         解決目標        対応時間帯
  P1       15 分            4 時間          24 時間 365 日（当番のスマホ）
  P2       1 時間           1 営業日        平日 8〜20 時
  P3       4 時間           3 営業日        平日 8〜20 時
  P4       1 営業日         10 営業日       平日 8〜20 時
  サービス要求  1 営業日      5 営業日        平日 8〜20 時
```

「一次応答は、『受け取った、誰が見る』と返すまでの時間。解決目標は、業務が戻るまでの時間。P1 は、四時間で戻す。戻せなくても、四時間の時点で、社長に報告する」

「一次応答の一言目は」

　西村が聞いた。

「『お問い合わせありがとうございます』でいい」

「治らないのが、役に立ちました」

　橘が聞いた。

「SSC の SLA と、SLO と、これは、どう違うんですか。会計上、三つの約束があると、混乱します」

　相殺後、十三。

「同じ考えの、別の層だ」

```
SLO（サーバーの話）    システムが、どれだけ止まらないか。可用性 99.9%。機械が測る
SLA（SSC）            SSC が、各社に、いつまでに処理するか。人が守る
SLA（サービスデスク）  サービスデスクが、問い合わせに、いつまでに答え、いつまでに戻すか。人が守る
```

「SLO は、システムの目標。SLA は、人の約束。SLO を守るために、SLA がある。四時間で戻せば、月に四十三分の予算のうち、四時間分を使う。P1 が月に一回あれば、SLO は守れない。だから、P1 は年に数回にしなければならず、そのために、問題管理と変更管理がある」

「四十三分は、資金繰り、と言いましたよね。二年前」

「言った」

「あのときは、まだ運用の話じゃなかった」

「今、運用の話になった」

「では、資金繰り表に足します。会計上」

　十四。

---

「一次と二次、というのは」

　西村が聞いた。

```
一次（L1）  サービスデスク。岡崎・西村
           手順書とナレッジで解決できるもの。パスワードリセット、権限追加、既知の不具合の回避策
           目標：チケットの 6 割を一次で閉じる
二次（L2）  システムごとの担当。受注→早瀬、EC・API→高梨・桐山、会計→橘チーム、基盤→赤海
           一次で解決できないもの。調査が要るもの
三次（L3）  ベンダー。社C 川辺、倉庫ベンダー、社F 真田、AWS サポート
           製品そのものの不具合。ヤマビコ側では直せないもの
```

「一次で六割、というのが目標だ。今は、たぶん二割だ。六割にするには、ナレッジが要る」

「ナレッジ」

「同じ問い合わせが、何度も来る。『Power BI が開かない』は、九割が、Entra ID の条件付きアクセスで、私物のスマホから開こうとしてる。それを、一次が知ってれば、一次で閉じる。知らなければ、岡崎さんが赤海に聞き、赤海が調べる。二回目からは、一次で閉じる。そのために、一回目の答えを、ナレッジに書く」

```
ナレッジ KB-0012
  症状      Power BI が「アクセスが拒否されました」で開かない
  原因      条件付きアクセス。Intune 管理外の端末からのアクセス
  回避策    会社支給の端末から開く。私物なら、Intune 登録を申請（サービス要求 SR-0004）
  恒久対策  なし（設計通りの動作）
  関連      ゼロトラスト
```

「KB-0001 は、何ですか」

　西村が聞いた。番号が飛んでいた。

「KB-0001 は、『今、買っていいか』への回答だ」

```
ナレッジ KB-0001
  症状      「今、買っていいか」と聞かれる
  原因      三上部長
  回避策    テレビ放映中・変更の窓の間は「だめです」。それ以外は「いいです」
  恒久対策  なし
  関連      KB-0002「ストア重くないか」（回答：重くないです）
```

「これで、一次で閉じられます」

　西村は、KB-0001 を、三日で暗記した。

「ナレッジは、志村さんの台帳と、田中さんの四十ページのマニュアルの、正しい姿だ。頭の中にあったものを、次の人が読める形にする。三か月で、百件書く。一次解決率は、それで五割を超える」

---

　三月の末、ベンダーとの約束を、整理した。

「三次は、ベンダーです。ベンダーにも、約束があります」

　早瀬が、契約書を並べた。岡崎が、契約書と聞いて来た。

```
ベンダー保守契約（抜粋）
  社C（受注 SaaS）    月 10 時間の保守。問い合わせは営業時間内。障害時は SaaS の SLA 99.9%。
                      版上げは 2 週間前に通知（← 今回、通知は来ていた。誰も読んでいなかった）
                      うち 1 時間は充電器の配達（関係構築）
  倉庫ベンダー        年間保守契約。平日 9〜17 時。電話とメール。緊急は翌営業日
```

「ITSM ツールが、インシデント INC-0903 を作り、P2 の札を貼りました。影響は会計だけで、緊急度は中。夜間なので、当番は鳴りません。翌朝八時、岡崎さんが一次で見て、既知のエラー KE-001 だと判断しました。社C が前夜、版を上げてた。ただし今回は、通知が変更チケット CHG-0058 として先週 CAB を通ってて、私が、staging で連携テストをしてました。staging では通ってた」

「本番で止まった」

「本番で止まりました。staging と本番で、社C 側の設定が一か所違ってた。九時、桐山さんが二次で見て、九時二十分に回避策で流し直し、業務が戻りました。MTTR 八十分。ただし、夜間の P2 なので、SLA の一営業日以内です」

「そのあと」

「事後レビューで、なぜを五回やりました。子供と近い形式で。staging と本番の社C 側の設定が違ってた理由は、staging の設定を、二年前に川辺さんが手で作ったからで、以降、本番の設定変更が staging に反映されてない。『だいたい同じ』が、SaaS の中に残ってました。問題 PRB-007 として登録し、恒久対策は、社C の設定を月に一度、本番から staging に複製する手順です。CAB で変更 CHG-0061 として承認され、十月の変更の窓で実施します。CMDB の SYS-02 の注意欄に、『staging 設定は本番から月次複製』が追記されました。川辺さんは、『弊社のなぜも五回やります』と、営業スマイルで言いました」

「四つの札が、全部出た」

「全部出ました。サービス要求が一枚、インシデントが一枚、問題が一枚、変更が二枚。全部、番号があって、担当があって、閉じるまで消えません。#2 と同じで」

「増えはしない」

「増えはしません」

「あと、三上部長は」

「同じ日の午後三時に、『今、買っていいか』を出しました。自動応答が『いいです』と返しました。変更の窓でも、テレビでも、P1 中でもなかったので。部長は買いました。テントでした。チケット SR-1183 は、自動で閉じました」

　赤海は椅子を回した。

　からあげ棒を、早瀬に差し出した。早瀬は食べた。

　それから、もう一本を、西村に差し出した。西村は初めてだった。

「……お問い合わせありがとうございます」

「問い合わせてない」

「癖です。いただきます」

　西村は食べた。食べながら、それを記録した。「9月xx日 xx:xx 赤海よりからあげ棒。西村、受領」。八年の癖は、からあげ棒にも及んだ。

「二月の三日間と、何が違う」

　早瀬は、少し考えた。

「二月は、通知が出て、『見ます』と書いて、消えました。今日は、通知が出て、札が貼られて、番号がついて、閉じるまで消えなかった。同じ連携が、同じ理由で止まった。違うのは、直った速さと、次に起きないための手順が、残ったことです。あと、西村さんが記録してることです」

「作るときは、作れば終わりだと思う。作ったものは、動き続けなければならない。動き続けさせるのは、作るより長い。三年作って、一年、運用を作った。これで、やっと、一枚目の図の注文データベースが、集計に使われずに、動き続ける」

「掃除ですね」

「社長の例えを使うな」

「三連続で当たった日の例えです」

「……三連続だったな」

「建てた奴は、掃除しない、も当たってました」

「俺は掃除してる」

「赤海さんは、建てて、掃除もしてます。支援の一環で」

　赤海は、それについて、何も言わなかった。串を缶に立てた。缶は八つになっていた。

> 作ることには終わりがある。運用には終わりがない。家は建てたら掃除。掃除代は建築費の十二倍。
> 四つの札。サービス要求、インシデント、問題、変更。麻雀ではない。札が違うと、やることが違う。
> 一つの窓口。全部の問い合わせと通知が来て、札を貼り、番号をつける。閉じるまで消えない。#2 と同じ。岡崎さんの甥。
> 優先度＝影響度×緊急度。SLA は人の約束、SLO は機械の目標。一次で六割、そのためにナレッジ。KB-0001 は部長。
> P1 は四つの役割。指揮者は手を動かさない。第一報は、わかっていないことと次の連絡時刻を。業務を戻すのが先。「使わないと思うけど念のため」が五十一分を作った。
> 事後レビューは非難しない。なぜを五回（子供と近い）。インシデントは閉じ、問題は原因が消えるまで閉じない。KE-005 は気のせい。
> 変更はインシデントの最大の原因。三種類。窓と凍結。CAB はタクシーではない。ベンダーの変更は、事前テストと当日確認。
> CMDB＝システムと連携と、オーナー・窓口・契約・EOL。固定資産台帳であり登記簿。EOL は予定されたインシデント。部長のスマホは載せない。
> 当番は五人。手当と休みは費用。人は減価償却できない。トイル（苦役）は五割以下。エラーバジェットは資金繰り。四月は当座貸越。
> 運用の費用は、作る費用の十二倍。買った後の値段。夜座が載った。
>
> 九枚目は、一枚目から八枚目を、動き続けさせるための図。
