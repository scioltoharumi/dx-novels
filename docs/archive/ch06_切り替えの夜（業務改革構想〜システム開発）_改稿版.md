# 切り替えの夜（改稿版）

## 第一章　システムを入れたい

「受注管理システムを入れろ」

　七月の経営会議で、大河内はそう言った。理由は三つあった。

　一つ目。丸嘉との連携が始まって二か月、丸嘉からの注文は、丸嘉の担当者がメールで送ってくる CSV を、営業の三上が倉庫にメールで転送し、倉庫の佐藤が倉庫システムに手で入れている。先週、同じ CSV が二回転送され、二十件が二重に出荷された。

「二回転送したのは、俺じゃない」

　三上が言った。

「部長です」

　梨乃が言った。

「……俺か」

「部長です」

　二つ目。法人顧客——山岳会や学校——からの注文は、電話と FAX で来る。営業事務が注文書を Excel に打ち込み、倉庫にメールし、経理の橘が会計システムに請求を手で入れる。先月、FAX の数字の読み間違いで、二十足のはずが二百足の請求書が出た。

　三つ目。EC の注文は自動で倉庫システムに流れるが、EC と丸嘉と法人で、同じ商品の在庫が三つの経路から引き当てられるため、EC で「在庫あり」と出た商品が、実は法人向けに全部押さえられていた、ということが月に数回起きている。

「三つの経路を、一つの受注管理に乗せる。梨乃、これは君がやれ。赤海は忙しい」

「赤海さんは、契約書の件名が『調査』なので、受注管理の導入は範囲外です」

「じゃあ梨乃だ」

「はい」

「システムってのはな」

　梨乃は待った。

「家みたいなもんだ。家は……建てる」

「はい」

「建てる前に、何部屋要るか決めろ」

　社長はそう言った。梨乃は「はい」と答えて、そのあとで気づいた。それは要件定義のことだった。

　梨乃は返事をする前に、一つ聞いた。

「予算と期限は」

「予算は千五百万まで。期限は来年三月。丸嘉の担当者が『御社の注文処理、大丈夫ですか』と言ってきてる。四月から丸嘉の取扱店舗が三倍になる」

---

　その日の午後、梨乃は小部屋に行った。赤海は、Terraform のファイルを開いていた。

「社長が、受注管理システムを入れろと言いました」

「聞いた」

「赤海さんは範囲外だそうです」

「範囲外だ。ただし、相談は範囲内だ」

「相談は、調査の一環ですか」

「調査の一環だ」

「赤海さんなら、何から始めますか」

　赤海は手を止めた。

「『システムを入れろ』は、社長の言葉だ。社長が本当に言いたいのは、『二重出荷と誤請求と在庫の食い違いをなくせ』だ。システムは、そのための手段の一つで、手段は他にもある。まず、今の業務がどうなってるかを、全部書け」

「業務フローですか」

「そうだ。ただし、今ある手順書を写すな。手順書には書いてないことが、現場で起きてる。倉庫と営業事務と経理に、一日ずつ張り付いて、何を、誰が、何分かけて、何件やってるかを数えろ。三つの経路それぞれで」

「一週間かかります」

「一週間で済むなら安い。これを飛ばして要件を書き始めると、半年後に『そんな業務は知らなかった』が出る」

「社長は『何部屋要るか決めろ』と言いました」

「……社長は、たまに当たる」

「半分です」

「半分だ」

---

　梨乃は、早瀬を連れて、一週間、現場を歩いた。

　月曜は倉庫。佐藤の一日を朝八時から追った。

　EC の注文は倉庫システムに自動で入ってくる。それを佐藤がピッキングリストに印刷し、棚から集め、梱包し、送り状を貼る。丸嘉の CSV は、三上から転送されたメールを佐藤が開き、倉庫システムに一件ずつ手で入れる。四十件で一時間。法人の注文は、営業事務からのメールを見て、これも手で入れる。

「佐藤さん、丸嘉の CSV、二回来たときは、どうやって気づくんですか」

「気づけません。前回は、同じお客さんの名前が二回続いたから、変だと思って三上部長に電話しました」

「部長は何と」

「『俺じゃない』と」

「部長でした」

「部長でした」

　火曜は営業事務。パートの吉田と小川が、FAX と電話の注文を Excel に打ち込む。FAX は一日に十五枚、電話は八本。Excel は「法人受注台帳_2026.xlsx」。打ち込んだら、倉庫と経理に、それぞれ別の形式でメールする。倉庫には商品と数量、経理には金額と請求先。

「二百足の件は」

「FAX の 20 が、手書きで 200 に見えたんです。私が打って、誰も確認しなくて、そのまま経理に行きました」

　吉田は言った。小川が付け足した。

「その FAX、まだ取ってあります。見ますか」

　梨乃は見た。確かに、200 に見えた。20 にも見えた。どちらにも見えた。

「これ、誰が見ても迷いますね」

「迷ったので、電話で確認しようとしたんですが、会長さんが山に登ってて、つながらなくて」

「山に」

「山岳会なので」

　水曜は経理。橘は、営業事務のメールを見て会計システムに請求を起こす。EC の売上は月末に Snowflake の経理マートから取るが、丸嘉と法人の分は手入力だ。月に百二十件。

「丸嘉の分は、丸嘉からも月末に『支払通知書』が来ます。それと私の入力を突き合わせて、合わないと丸嘉に問い合わせる。先月は八件合いませんでした。会計上、八件は多いです」

　木曜と金曜は、梨乃と早瀬でフローを描いた。三つの経路を、横に並べた。

```
        EC                    丸嘉                       法人
受注    ECサイト（自動）        メールで CSV（三上が転送）    FAX・電話（営業事務が Excel 入力）
在庫    倉庫システムが引当      佐藤が手入力後に引当           佐藤が手入力後に引当
出荷    倉庫システム            倉庫システム                  倉庫システム
請求    自動（決済代行）        橘が手入力（月末に突合）       橘が手入力
入金    自動                   丸嘉から月末振込               振込を橘が消し込み
```

　そして、数えた。

```
手作業の時間（月）
  佐藤の手入力          丸嘉 40件/日 × 1.5分 + 法人 25件/日 × 2分  ≒ 45時間
  営業事務の入力と転送   FAX・電話 23件/日 × 6分                   ≒ 46時間
  橘の請求入力と突合     120件 × 8分 + 突合 6時間                   ≒ 22時間
  三上の転送と問い合わせ                                          ≒ 8時間
  合計                                                          ≒ 121時間/月

事故（過去6か月）
  二重出荷    3回（計 52件、回収と再発送で約 30万円）
  誤請求      5回（うち1回は 200足、取引先との関係に影響）
  在庫食い違い 月 3〜4回（EC で「在庫あり」→ 実は法人向けに引当済み、キャンセル対応）
```

「三上部長の八時間、というのは」

　早瀬が聞いた。

「転送が一時間。残り七時間は、『俺じゃない』と説明する時間」

「……それ、書いていいんですか」

「書かない。数字だけ書く」

　金曜の夕方、梨乃はこの二枚を赤海に見せた。赤海は三分見て、言った。

「これで、『システムを入れる』が、『月百二十一時間と、半年で八回の事故を、どうするか』に変わった。ここからが、構想だ」

「部屋の数を、決めるんですね」

「社長の例えを使うな」

「使いません」

　梨乃はノートに書いた。

> 「システムを入れろ」は手段の言葉。目的は、その裏にある痛み。
> 痛みは、現場に張り付いて、数えて、金額にする。手順書を写さない。
> As-Is（現状）を描くのは、To-Be（あるべき姿）との差を測るため。
> （20 と 200 はどちらにも見える。会長は山にいる）

---

## 第二章　あるべき姿

　八月の第一週、梨乃は「構想」を書き始めた。書き始めて、すぐに止まった。

「赤海さん、あるべき姿、というのが、うまく書けません。『三つの経路が一つのシステムに入る』と書くと、それは結局システムの話で」

「システムの話になるのは、まだ論点が整理できてないからだ。何を解くのか、を先に分けろ」

　赤海はホワイトボードに、三つの問いを書いた。

```
大論点   三つの注文経路の受注業務を、どうすれば事故なく、少ない手間で回せるか

中論点1  注文の「入口」を、どうするか
         ・丸嘉の CSV メールを、システム連携（API）に変えられるか
         ・法人の FAX・電話を、やめられるか。やめられないなら、どう受けるか
中論点2  在庫の「引当」を、どこで一元化するか
         ・三経路の注文が、同じ在庫を、同じ場所で、同じ順番で引き当てる
中論点3  請求と入金を、どう自動化するか
         ・丸嘉の支払通知との突合を、人がやらなくていい形にできるか
中論点4  誰が、いつ、何を確認するか
         ・二重・誤入力を、システムが止めるか、人が止めるか
```

「中論点 1 を見ろ。『法人の FAX をやめられるか』は、システムの話ではない。業務の話だ。山岳会のおじいさんが FAX で注文してくるのを、『これからはウェブで』と言えるかどうかは、三上さんが決める話で、システム屋が決める話ではない」

「業務を変えるか、システムで吸収するか」

「そうだ。FAX をやめられれば、法人の注文は EC と同じ入口に乗る。やめられなければ、FAX を読み取って入力する仕事が残り、その仕事をシステムで支える必要が出る。どちらを選ぶかで、作るものが変わる。だから、システムを決める前に、業務をどこまで変えるかを決める」

---

　梨乃は、三上のところに行った。

「法人のお客さんに、FAX と電話をやめてもらって、ウェブから注文してもらうことは、できますか」

　三上は腕を組んだ。

「半分は、できる。学校とか、若い会長の山岳会とかは、むしろそのほうが楽だと言う。残り半分は、無理だ。八十歳の会長が、FAX しか使わない。そのお客さんは、年間三百万買ってくれる」

「じゃあ、FAX は残る」

「残る。ただ、FAX を営業事務が打ち込むのを、俺が一回確認する、というのはできる。二百足の件は、誰も見なかったのが問題だ」

「部長が、毎回確認するんですか」

「毎回だ」

「山に登ってても」

「山に登ってても、電話は通じる」

「会長は通じませんでした」

「会長は八十だ」

　梨乃はメモした。「FAX は残す。ただし、入力後に営業が確認する工程を足す。半分はウェブへ誘導」。

　次に丸嘉の担当者に、オンラインで聞いた。

「CSV のメールではなく、API で注文を送ってもらうことは」

「できます。むしろ、うちはそのほうが楽です。御社が API を受ける側になれば、うちの発注システムから直接送ります。仕様書を送ります」

「三上が転送しなくてよくなる」

「三上さんが転送しなくてよくなります」

　丸嘉の担当者は、少し笑った。二回転送の件は、丸嘉にも知られていた。

　中論点 1 の半分が、これで決まった。

---

　八月の第三週、梨乃は「構想書」を一枚にまとめた。

```
受注業務改革 構想書（案）

1. 目的
   三つの注文経路（EC・丸嘉・法人）の受注から請求までを一つの業務に統合し、
   手作業を月 121 時間から 30 時間以下に、事故を半年 8 件からゼロにする。

2. 業務の変え方（システムより先に決めること）
   ・丸嘉：CSV メールをやめ、API で受ける
   ・法人：ウェブ注文への誘導を進める。FAX・電話は残すが、入力後に営業が確認する
   ・在庫：三経路の引当を一か所にする。EC の「在庫あり」は、法人・丸嘉の引当後の数
   ・請求：丸嘉・法人の請求データを会計に自動連携。橘の手入力をなくす

3. システムに求めること（要件の元）
   ・三経路の注文を一つの受注台帳で持つ
   ・在庫引当を一元化し、倉庫システムへ出荷指示を送る
   ・請求データを会計システムへ送る
   ・商品・顧客は、既存の正本（xref_product / xref_customer）と紐づく
   ・社員のログインは Entra ID の SSO

4. 目標指標（KPI）
   手作業時間：121h → 30h／月
   二重出荷・誤請求：8件／半年 → 0
   在庫食い違いによるキャンセル：月 3〜4件 → 0
   丸嘉 支払通知との不一致：月 8件 → 0

5. 体制
   スポンサー：大河内
   PM：佐伯　　PMO 補佐：早瀬
   業務オーナー：三上（受注）、佐藤（出荷）、橘（請求）、志村（商品）
   技術：赤海（連携・基盤、調査の一環）、高梨・桐山（API 開発）

6. 予算と期限
   1,500 万円以内、2027 年 3 月稼働

7. やらないこと
   ・倉庫システムの置き換え（別プロジェクト）
   ・EC サイトの改修（在庫表示の数の元を変えるだけ）
   ・会計システムの置き換え
```

「七番が、一番大事だ」

　赤海は、構想書を読んで言った。

「『やらないこと』を書かないと、プロジェクトの途中で全部が入ってくる。三上さんは受注画面に顧客の購入履歴を出したいと言うし、志村さんは商品登録画面をこっちに移したいと言う。全部、良い話だ。全部やると、三千万と二年になる」

「断れますか」

「断るのは、梨乃さんじゃない。この構想書に社長が印を押せば、断るのは構想書だ。『やらないことに書いてあります』と言えばいい。だから、社長に印を押させる前に、三上さんと志村さんと橘さんと佐藤さんに、この一枚を見せて、七番に文句を言わせろ。文句が出尽くしてから、社長に持っていく」

「五番の『調査の一環』は、消したほうがいいですか」

「消せ。社長が読んで、契約書を思い出す」

「思い出したら、どうなるんですか」

「たぶん、『続けろ』と言う」

　梨乃はその週、四人と個別に話した。

　三上は「購入履歴は、次でいい。あと天気も出したかったが、次でいい」と言った。天気は聞いていなかった。志村は「商品登録は、今の画面で困ってない。備考欄はないが」と言った。橘は「会計システムの置き換えは、私が反対する。会計上は」と言った。佐藤は「倉庫システムは、来年クラウド版になるんですよね。それまで待ちます。あと、これは請求書に載りますか」と言った。

「何がですか」

「赤海さんの分」

「載りません。調査の一環です」

「そうですか」

　佐藤は、それだけを確認して帰った。

　八月の最終週、経営会議で大河内が印を押した。押しながら、「部屋の数は、これでいいんだな」と言った。梨乃は「はい」と答えた。当たった半分の日だった。

　ステアリングコミッティ——月に一度、社長と業務オーナーが集まって、進捗と判断をする会——が、九月から始まることになった。

　梨乃はノートに書いた。

> 構想＝目的、業務の変え方、システムへの要求、指標、体制、予算・期限、やらないこと。
> システムより先に、業務をどこまで変えるかを決める。決めるのは業務オーナー。
> 「やらないこと」は、後で断るための盾。印を押す前に、文句を出し切らせる。
> 論点は分けて書く。分けると、どれが業務の話で、どれがシステムの話かが見える。
> （天気は、次でいい）

## 第三章　要望と要件

　九月、要件定義が始まった。

　梨乃は、週に二回、業務オーナーを集めて二時間のワークショップを開いた。最初の回で、三上が言った。

「受注画面には、お客さんの過去三年の購入履歴と、今の会員ランクと、担当営業と、前回の商談メモが出てほしい。あと、見積書もここから出したい。あと、天気」

「天気は、次でいいって言いましたよね」

「言ったが、やっぱり欲しい。山の天気で注文が変わる」

　梨乃は、それをそのまま書き留めそうになって、止まった。構想書の七番を思い出した。

「三上さん、それは『要望』です。今日集めているのは『要件』です」

「何が違う」

　赤海が、その日は会議の隅に座っていた。からあげ棒は、しょうゆ味だった。緊張している。

「要望は、あると嬉しいこと。要件は、ないと目的が達成できないこと。構想書の目的は、手作業を三十時間にして、事故をゼロにすることだ。購入履歴が受注画面に出なくても、二重出荷は防げる。だから要望だ。天気が出なくても、二重出荷は防げる。要望だ。見積書は、法人の受注の前に必ず出してるなら、それがないと法人の受注が回らない。それは要件かもしれない」

　三上は少し考えた。

「見積書は、営業事務が Excel で作ってる。それは今のままでいい。受注画面に出なくていい」

「じゃあ要望に入れておきます。次のプロジェクトのために」

　梨乃は、ホワイトボードに二つの枠を作った。左が「要件」、右が「要望（今回はやらない）」。

「俺の天気は」

「右です」

「右の枠、いい名前だな」

「名前じゃなくて、枠です」

　ワークショップのたびに、右の枠が増えていった。三上の天気は、右の一番上に、ずっと残った。

---

　要件は、三つの層に分けて書いた。赤海の助言だった。

```
業務要件   業務として、何ができなければならないか
           例：丸嘉からの注文を、人手を介さず受注台帳に取り込める
              法人の FAX 注文を入力したあと、営業が承認するまで出荷指示が出ない
              三経路の注文が、同じ在庫から、受注順に引き当てられる

機能要件   システムとして、何を持たなければならないか
           例：丸嘉の発注 API を受け付ける受信口
              受注に「承認待ち」「承認済み」の状態を持ち、承認済みのみ倉庫へ送る
              在庫引当は受注台帳が一元で行い、倉庫システムには出荷指示のみ送る
              受注の重複チェック（同一取引先・同一注文番号は二件目を拒否する）

非機能要件 どのくらい速く、どのくらい止まらず、どのくらい守るか
           例：丸嘉 API は 3 秒以内に応答
              平日 8〜20 時は 99.5% 稼働
              ログインは Entra ID の SSO。ロールは受注・出荷・請求・管理者の四つ
              受注データは 7 年保持
```

「業務要件だけだと、システム屋は何を作ればいいかわからない。機能要件だけだと、業務の人は何のためかわからない。両方書いて、一対一で紐づける。『この機能要件は、この業務要件のためにある』と。紐づかない機能要件は、要望が紛れ込んでる」

　早瀬が、紐づけの表を作った。業務要件が十八、機能要件が四十二。紐づかない機能要件が三つ見つかり、三つとも右の枠に移った。

「三つのうち一つが、『受注画面に天気を表示』でした」

「誰が入れたんですか」

## 終章　一枚目の図

　六月、早瀬は倉庫システム移行の構想書を書き始めた。書き始めて、すぐに止まった。梨乃の席に来て、言った。

　梨乃は、自分のノートを開いた。最初のページに、二年前の九月、こう書いてある。

> 業務システムのデータベースは、業務を動かすためのもの。
> 集計のために使うと、業務のほうが止まる。
> （部長のテントが止まる。部長の家のテントの数は不明）

　最後のページに、梨乃は書いた。

> 「システムを入れろ」は手段の言葉。痛みを、現場で数えて、金額にする。20 と 200 はどちらにも見える。
> 構想＝目的、業務の変え方、指標、体制、予算、やらないこと。業務を先に決める。部屋の数を決める（社長）。
> 要望と要件を分ける。三層で書き、紐づける。増えたら記録する。優先度は先に決める。天気は右の枠。
> 作るか買うか借りるか。借りるなら業務を合わせる。基準を先に書く。部長はデモに弱い。
> 設計書に書いてないことは作られない。異常時が価値。決めていないことを見つけて、決める人を記録する。
> 進捗は作業の名前で。変更は手順で。テストは異常系まで。UAT の基準は先に。九割は五割。
> 切替は戻せる形で。リハーサルは二回。判定は表で。印鑑の欄。成功の姿は「誰も気づかない」。
> 定着＝運用設計、効果測定、振り返り。プロジェクトは終わるが、システムは終わらない。
>
> 二年前、一枚目の図を描いたとき、六枚目は見えていなかった。
> ただ、一枚目に「集計に使うな」と書いたから、二枚目が要った。
> 二枚目の正本が割れていたから、三枚目の人の正本が要った。
> 三枚目で壁をなくしたから、四枚目の門番が要った。
> 四枚目で一台では足りないとわかったから、五枚目の家畜が要った。
> 五枚全部があったから、六枚目は、作れた。
>
> 一枚ずつでいい。ただし、一枚目に、本当のことを書く。
> （テントの数は、まだ不明。調査は、まだ続いている。佐藤さんは載せたがっている）

## 付録　登場した仕組みと用語

| 物語での呼び方 | 正式名称 | 役割 |
|---|---|---|
| 現場に張り付いて数える | 現状業務分析（As-Is） | 手順書でなく実態。件数・時間・金額に落とす。20 と 200 |
| 痛み | 経営課題・業務課題 | 「システムを入れろ」の裏にある目的 |
| 何を解くのか | 論点設計 | 大論点→中論点。業務の話とシステムの話を分ける |
| あるべき姿 | To-Be | 業務の変え方を先に決め、システムはその後 |
| 部屋の数 | 構想書 | 目的・業務・要求・KPI・体制・予算・やらないこと。社長が当てた回 |
| 社長のいる会議 | ステアリングコミッティ | 月次で進捗と判断。変更要求の承認 |
| 右の枠 | 要求管理（要望と要件） | 要件＝ないと目的が達成できない。要望は次の盾。天気は右 |
| 三層 | 業務要件／機能要件／非機能要件 | 業務と機能を一対一で紐づける。鉛筆も疑う |
| 落とす順番 | 優先度（MoSCoW） | Must / Should / Could / Won't。ロシアではない |
| 作るか買うか借りるか | スクラッチ／パッケージ／SaaS | 業務が標準的なら借り、業務を合わせる |
| 当てる | Fit & Gap | Gap は業務で吸収・連携で作る・諦める。四割超でやめる。早瀬が当てた回（本） |
| 提案依頼 | RFP | 選ぶ基準を先に書いて見せる。部長はデモに弱い |
| 時間で払う・成果で払う | 準委任／請負 | 融通と保証のトレードオフ。夜座は準委任で「適宜」 |
| 紙で合意 | 基本設計（外部設計） | 業務・画面・帳票・IF・データ。使う側が承認。三百回の「思っていたのと違う」を先に |
| 作る側の内部 | 詳細設計 | 基本設計の IF 仕様が両者の約束 |
| 決めていなかったこと | 設計レビュー | 見つけて、業務オーナーが決め、名前を記録。所要三十分（本題五分） |
