# 業務改革の考え方・手法・整理軸 一覧（第6章 改番の材料）

第6章「切り替えの夜」に出た27の概念を起点に、業務改革（BPR・業務システム導入）で使われる考え方・Tips・整理軸・手法を工程順に棚卸しした。
次の段で「第6章の改番（全部盛り）」を書くための材料であり、本文ではない。

## 凡例

| 印 | 意味 |
|---|---|
| ◎ | 第6章に既出（付録の27語、または本文で名前つきで出ている） |
| △ | 第6章に現象としては出ているが、名前・型として整理されていない |
| × | 第6章に未出 |
| chNN | 他の話の付録で既出（そちらの呼び方で引ける） |

各表の列は「名称｜一言の意味｜Tips・使いどころ｜第6章」。

## 0. 全体を貫く三つの動詞（第6章で既に立っている芯）

| 動詞 | 中身 | 対応する概念 |
|---|---|---|
| 先に決める | 判断の基準を、判断の前に作る | MoSCoW、RFP の評価基準、UAT 合格基準、ロールバック基準、カットオーバー判定表 |
| 分ける | 混ざると断れなくなるものを分けて置く | 業務／システム、要望／要件、基本設計／詳細設計、利用契約／導入支援 |
| 記録する | 後から作り話にならないよう、理由と決めた人を残す | 増えた要件の理由、設計レビューの決定者、変更要求番号、振り返り |

改番で追加する概念も、この三つの動詞のどれかに紐づけて出すと、章の芯がぶれない。

## 1. 改革の型・思想（どの流儀で変えるか）

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| BPR（Business Process Reengineering） | 業務を部分改善でなく根本から設計し直す | Hammer & Champy。「今のやり方を自動化するな、やり方を捨てろ」。改善（Kaizen）との違いを最初に説明する | △（やっているが名前なし） |
| 業務改善と業務改革の違い | 改善＝今の流れを速くする。改革＝流れ自体を変える | 経営者が「改善」を求めているのに PM が「改革」を始めると衝突する。どちらの話かを冒頭で確認 | × |
| リーン／TPS（トヨタ生産方式） | 価値を生まない動き（ムダ）を減らす | 7つのムダ（作りすぎ・手待ち・運搬・加工・在庫・動作・不良）。事務業務にも当てはめられる（転記＝運搬、承認待ち＝手待ち） | × |
| 3現主義 | 現場・現物・現実を自分の目で見る | 手順書を写さない。第6章の「現場に張り付いて数える」の正式な呼び名 | △ |
| TOC（制約理論） | 全体の速さはボトルネックで決まる | ボトルネック以外を速くしても意味がない。承認者一人が全件を「じっくり見る」のがボトルネック | △（三上の承認6時間） |
| シックスシグマ／DMAIC | 定義→測定→分析→改善→管理の五段階 | ばらつき（20 と 200 の誤読）を統計的に減らす発想。中小企業では「測定してから直す」の順序だけ借りればよい | × |
| ECRS | 排除（Eliminate）→結合（Combine）→入替（Rearrange）→簡素化（Simplify）の順で見直す | 「自動化」より前に「なくせないか」を問う。FAX 入力を自動化する前に FAX をやめられないか | × |
| 標準化→簡素化→自動化 | 自動化は最後。先に業務を揃え、減らす | バラバラのまま自動化すると、バラバラが固定される | ch07（集約・標準化・自動化） |
| Fit to Standard | 製品標準に業務を合わせる | 「借りるなら業務を合わせる」の正式名称 | ◎（ch08 でも既出） |
| デジタイゼーション／デジタライゼーション／DX | 紙を電子に／業務を電子前提に組み直す／事業を変える | 「システムを入れろ」は一段目。何段目の話をしているかで予算も体制も変わる | × |
| ゼロベース思考 | 今のやり方が無いものとして設計する | 「なぜこの承認があるのか」に答えられない工程は候補 | × |
| PDCA／OODA | 計画→実行→評価→改善／観察→状況判断→決心→行動 | 定着後の継続改善は PDCA。切替当日の対応は OODA | △ |
| ジョブ理論（Jobs to be Done） | 利用者が本当に片付けたい用事は何か | 「天気」の裏のジョブは「配送日を決めたい」かもしれない。要望を却下する前にジョブを聞く | × |

## 2. 現状分析（As-Is）の手法

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| 現場観察（Gemba Walk）／シャドーイング | 担当者の横に座って一日を見る | 「何をしていますか」より「今のは何ですか」。手順書に無い動きが本命 | ◎ |
| 業務ヒアリング設計 | 誰に・何を・どの順で聞くか | 管理者→担当者→隣の部署の順。同じ質問を三人にして食い違いを拾う | △ |
| 業務棚卸し（業務一覧） | 部署の業務を全部書き出す | 頻度（日・週・月・年）と所要時間を添える。年一回の業務が移行で抜ける | × |
| 業務量調査（工数調査） | 業務ごとの時間を測る | タイムスタディ（測る）／ワークサンプリング（抜き取り）／自己申告。自己申告は三割少なく出る | ◎（月121時間） |
| 業務フロー図（スイムレーン） | 誰が・何を・どの順で。部署ごとにレーンを分ける | レーンを跨ぐ矢印の数＝手戻りと転記の数。BPMN は記法の標準 | △ |
| データフロー図（DFD） | 情報がどの帳票・システムを通るか | 「同じ数字を何回入力しているか」を数える | × |
| 帳票棚卸し | 使っている紙・Excel を全部集める | 野良 Excel、個人フォルダのマクロ。廃止候補と移行対象がここで決まる | × |
| システム関連図 | どのシステムがどの経路でつながっているか | CSV 転送・メール添付も「連携」として描く。二重転送はここで見える | △ |
| 転記マップ | 人が数字を写している箇所を全部印す | 転記箇所＝誤読とミスの発生源。20 と 200 | △ |
| 例外処理の洗い出し | 「通常はこうだが、○○のときは」を集める | 例外の数が要件の数を決める。返品はここで拾えた | △（佐藤の返品） |
| 属人化マップ（スキルマップ） | 誰しかできない業務はどれか | 移行と教育の優先順位。BCP にもつながる | ch10（属人化リスク） |
| リードタイム分析／VSM | 受注から出荷までの時間を、作業時間と待ち時間に分ける | 待ち時間が八割。承認待ちを減らすほうが入力を速くするより効く | × |
| 事故・ミス分析（パレート図） | 事故を種類別に数え、多い順に並べる | 上位二割の原因で八割の事故。半年八件を型で分ける | △ |
| 根本原因分析（5 Whys／特性要因図） | なぜを五回。人・方法・設備・材料で原因を分類 | 「担当者の注意不足」で止めない | ch09（RCA） |
| 隠れ業務（シャドーワーク） | 手順書に無いが誰かがやっている調整・確認 | 三上が「入力後に自分で確認する」工程。これを要件に入れるか、なくすか | △ |
| 声の大きい人バイアス | ヒアリングで要望が特定の人に偏る | 発言者を記録し、件数や時間の裏付けと突き合わせる | △（三上） |
| 定量化の三点セット | 件数×時間×単価で金額にする | 経営会議で通る言葉は金額。時給を掛けて年額にする | ◎ |

## 3. 課題設定・論点整理

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| 論点設計（大論点→中論点→小論点） | 解くべき問いを階層に分ける | 小論点は「○○は△△か？」の形まで落とす | ◎ |
| イシューツリー／ロジックツリー | 問いを枝分かれで分解する | MECE（漏れなくダブりなく）を意識するが、完璧より本質 | △ |
| 仮説思考 | 調べる前に答えの当たりをつける | 「おそらく転記が原因」と置いてから数えに行く。外れたら記録する | × |
| So What／Why So | それで何が言えるか／なぜそう言えるか | 構想書の各行に「だから何」を付ける | × |
| 空・雨・傘 | 事実→解釈→行動を分けて書く | 「手作業121時間（空）→ 転記が原因（雨）→ 経路統合（傘）」 | × |
| 課題解決の五階層 | あるべき姿→問題→課題→原因→真因 | 「システムが無い」は原因でなく症状。真因は「三経路が別々に育った」 | × |
| 問題と課題の区別 | 問題＝あるべき姿との差。課題＝差を埋めるためにやること | 「二重出荷が起きる」は問題。「経路を一本化する」が課題 | △ |
| 人・プロセス・ルール・システムの切り分け | 原因がどこにあるかを四つに分ける | システムで解ける原因は四つのうち一つだけ | × |
| 経営課題→業務課題→システム課題の三段翻訳 | 「利益が出ない」を「業務の何が」「システムの何が」まで落とす | 逆向きの翻訳（システム→経営）が構想書の効果欄になる | △ |
| 症状と真因 | 目に見える困りごとと、それを生む仕組み | 症状に薬を出すと再発する | △ |
| 前提条件と制約条件 | 変えられない条件（期限・予算・法令・取引先）を先に書く | 「会長は FAX しか使わない」は制約。制約は構想書に明記する | △ |
| 「与件に無いこと」の明示 | 分かっていないことを、分かっていないと書く | 推測で埋めない。テントの数は不明 | △ |

## 4. あるべき姿（To-Be）の設計

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| To-Be 業務フロー | 変えた後の流れを As-Is と同じ記法で描く | 同じ記法で描くと差分が数えられる。差分＝チェンジの量 | ◎ |
| 業務の三分類（判断／処理／例外） | 人が判断する業務、機械で処理できる業務、型に嵌らない業務 | 処理は自動化、判断は残す、例外は型化するか件数を減らす | ch07（判断業務と処理業務） |
| 例外の設計 | 例外率を下げるか、例外を標準の一種にするか | 例外を全部システムに入れると要件が倍になる。「月に一件なら手作業」も設計 | △ |
| 承認設計 | 承認は「見る」でなく「止める」ためにある | 全件承認は承認ではなくボトルネック。金額・条件で自動承認と分ける | △（三上の承認） |
| 業務ルールの明文化（ディシジョンテーブル） | 条件と結果を表にする | 「請求単価は受注時か出荷時か」の類はここに載る。設計レビューの23件の予防 | △ |
| 職務分掌・内部統制 | 一人で完結させてはいけない業務を分ける | 受注と請求を同一人物が触れない設計。監査で必ず聞かれる | ch07（職務分掌） |
| マスタ整備の先行 | 取引先・品目のマスタを先に揃える | 移行エラーの大半はマスタ不一致。第2章の名寄せがここに効く | ch02（名寄せ） |
| プロセスオーナー制 | 業務の流れ全体に責任を持つ人を一人決める | 部署ごとの業務オーナーと別に、経路横断の責任者を置く | △（四人の業務オーナー） |
| 業務 KPI 設計 | リードタイム・処理件数・エラー率・工数 | 「手作業時間」と「事故件数」のほかに「受注から出荷までの日数」を持つと効果が語りやすい | ◎ |
| 定常／非定常の分離 | 毎日の流れと、月末・年度末・キャンペーン時を分ける | 非定常の設計漏れが本番三か月後に出る | × |
| 効果×実現難易度マトリクス | 施策を効果と難しさで四象限に置く | 右上から着手。左上（効果大・難）は次期 | × |
| クイックウィン | すぐ効く小さな施策を先にやる | 現場の信頼を買う。「CSV の二重転送防止」は一週間でできた | × |
| 廃止（やめる設計） | 業務そのものをなくす | 帳票の廃止、承認段階の削減。「やらないこと」の業務版 | △ |
| 自動化の適否（頻度×定型度） | 頻度が高く定型な業務だけ自動化する | 低頻度・非定型は人。RPA は「つなぎ」であって「改革」ではない | ch07（RPA） |
| チェンジ・インパクト分析 | 誰の仕事が、どう変わるかを人単位で書く | 教育計画と抵抗対策の入力になる。「営業事務の FAX 入力が消える」を人の名前で書く | × |
| 暫定業務（ブリッジ） | 切替までの間、どう回すか | 段階切替の期間中、新旧が混在する業務手順を作る | △ |

## 5. 構想・ビジネスケース・体制

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| 構想書 | 目的・業務の変え方・要求・KPI・体制・予算・やらないこと | 一枚。印を押す前に文句を出し切らせる | ◎ |
| プロジェクト憲章（チャーター） | 目的・権限・体制・期限を経営者が承認した文書 | PM の権限（何を自分で決めてよいか）を書く。構想書と兼ねてよい | △ |
| スコープ定義（In／Out） | 対象と対象外を明記する | 「やらないこと」の正式名称。Out を書かない構想書は膨らむ | ◎ |
| ビジネスケース／投資対効果（ROI） | 費用と効果を金額で並べる | 効果は削減・回避・創出に分ける。事故八件の損失額は「回避」 | △ |
| 回収期間／NPV | 何年で元が取れるか／将来の効果を現在価値に直す | 中小企業は回収期間で十分。三年以内が目安 | × |
| 費用の分類 | 初期費用・ランニング・内部工数 | 内部工数（現場の人が会議に出る時間）を費用に入れると、業務オーナーの本気度が変わる | △ |
| 予備費（コンティンジェンシー） | 想定外のための予算枠 | 一〜二割。「部屋を一つケチると後悔する」の正式名称 | △ |
| ステージゲート | 工程の節目ごとに続行・中止を判断する | 要件定義後、選定後、UAT 後。撤退基準も先に書く | × |
| 撤退基準 | どうなったらやめるか | Gap 四割超で SaaS をやめる、はこれ。プロジェクト全体にも要る | △ |
| ベネフィット実現管理 | 効果が出たかを稼働後に追う仕組み | 効果測定の担当と時期を構想書に書く。プロジェクト終了後に誰も測らないのが普通 | △（五月の効果測定） |
| KGI／KPI ツリー | 最終目標と、それを構成する指標の木 | 「事故ゼロ」の下に「転記箇所ゼロ」「二重転送ゼロ」を置く | △ |
| ステークホルダー分析 | 影響の大きさ×関心の高さで関係者を四象限に置く | 影響大・関心低の人（会長、丸嘉）が後で止める | × |
| 体制図と役割 | スポンサー・PM・PMO・業務オーナー・キーユーザー・ベンダー | 業務オーナーは「決める人」、キーユーザーは「試す人」。分けて置く | △ |
| RACI | 実行・説明責任・相談・報告を表にする | 「誰が決めるか」が空欄の仕事が、設計レビューの23件になる | × |
| 意思決定機関（ステアリングコミッティ） | 月次で判断する場 | 報告の場ではなく決める場。決めることが無い月は開かない | ◎ |
| エスカレーションルール | 誰が、いつ、誰に上げるか | 「二日止まったら PM、一週間止まったら社長」を先に決める | × |
| リスク登録簿 | 起きるかもしれないことと、起きたときの手 | 発生確率×影響度で並べる。丸嘉の API 遅延はここに載るべきだった | × |
| 経営者のコミットメント | 経営者が自分の言葉で目的を語り、判断に出てくる | 「印を押す」で終わらせず、切替判定にも出す | ◎ |
| 前提条件（アサンプション）ログ | 検証していない前提を一覧にする | 「丸嘉は API で送れる」は前提。前提が崩れたときの手を添える | × |

## 6. 要件定義

| 名称 | 一言の意味 | Tips・使いどころ | 第6章 |
|---|---|---|---|
| 要望と要件 | 要件＝ないと目的が達成できない。要望＝あると嬉しい | 右の枠 | ◎ |
| 業務要件／機能要件／非機能要件 | 何をする仕事か／画面は何をするか／速さ・安全・可用性 | 一対一で紐づけ、紐づかないものを疑う | ◎ |
| MoSCoW | Must／Should／Could／Won't | 間に合わないとわかる前に決める。Must が七割を超えたら優先度ではない | ◎ |
| ユースケース／ユーザーストーリー | 「誰が・何のために・何をする」の形で書く | 「営業事務が、二重出荷を防ぐために、同じ注文番号を弾く」。機能でなく目的で書ける | × |
| 受入基準（Given／When／Then） | 要件ごとに「こうなったら合格」を書く | UAT の合格基準を要件定義の時点で書く。後から書くと甘くなる | △ |
| トレーサビリティマトリクス | 業務要件→機能要件→設計→テストの対応表 | 鉛筆の天気はここで見つかった。テスト漏れもここで見つかる | ◎（紐づけ） |
| 非機能要求グレード | 性能・可用性・運用・移行・セキュリティ等の項目表（IPA） | 中小企業は「同時利用者数」「営業時間内の停止許容」「バックアップ」だけでも決める | △ |
| 要件の検証可能性（SMART） | 測れる形で書く | 「速く」でなく「一覧表示が三秒以内」 | △ |
| 業務ルール表 | 条件と結果を表にした要件 | 割引条件、承認条件、請求タイミング | △ |
| データ要件（CRUD 図） | どの画面がどのデータを作成・参照・更新・削除するか | 「誰も更新しないデータ」「誰も参照しないデータ」が見つかる | × |
| 権限マトリクス | 役割×機能で、できることを表にする | 承認者・入力者・閲覧者。SSO と一緒に設計する | △（社B の SSO） |
| 帳票要件 | 出力する紙・PDF・CSV の一覧と項目 | 請求書に載る項目。佐藤の件はここで決める | △ |
| 異常系要件 | 失敗したとき、途中で止まったとき、二回来たとき | 再送による二重出荷は異常系要件の漏れ | ◎ |

## 18. 改番で決めるべきこと（設計判断）

1. **一章に全部載せるか、分冊にするか。** 追加候補は約110。既存27と合わせて約140を一話に載せると、付録が本文になる。案として、(a) 本文は既存の筋のまま、各章末の「語録」を「語録＋軸」に拡張して概念を増やす、(b) 第6章を上下二話に分ける、(c) 本文に載せるのは各章五〜八個に絞り、残りは付録の表で対応する。推奨は (c)＋付録拡張。
2. **既存の筋を保つか、新しいプロジェクトにするか。** 受注管理の筋は他章（ch01・ch02・ch09）と人物・出来事が結びついている。筋を変えると他章の整合が崩れる。推奨は筋を保つ。
3. **ファイルの扱い。** `content/ch06_...改稿版.md` を上書きするか、`ch06` を改番して別ファイルにするか。上書きすると `meta/novels/ch06.json` の章別あらすじ・lessons・quotes も更新が要る。
4. **他章既出の概念（ch02 名寄せ、ch07 職務分掌、ch09 RCA など）を第6章でも出すか。** 出すなら「第2章で出た名寄せ」のように、既出を前提にした短い言及にとどめる。
