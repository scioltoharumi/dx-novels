# 入金消込の業務改革と AI エージェント 実務解説

番外編『二十三本の川』の別冊。小説で掴んだ考え方を、実際の案件で使える手順・表の型・判断基準に落とす。

- **小説の役割**: なぜ消込が難しいのか、何から手を付けるのか、AI をどこに置くのか、という骨格を記憶に残す
- **この資料の役割**: 調査の設計、効果の試算、要件定義書の目次、評価の数え方、法令の確認先まで、手を動かすための型を渡す
- **到達目標**: 入金消込の業務改革と AI 導入の案件で、現状分析から要件定義までを主導できること

> 数値は作中の例。法令・税務は執筆時点（2026年）の整理で、最新の条文・運用基準と専門家の確認を前提にする。

---

## 0. 全体の流れ

```
工程               中心の問い                                  主な成果物
1 現状を数える      何が、何件、何時間、どれだけ滞留しているか     請求元一覧・例外の分類表（件数×時間×滞留）
2 生まれた場所     その例外の情報は、どこで生まれ、誰が持つか     発生源マップ・制御可能性の切り分け
3 清流化を設計     上流で、どの情報を、どの形で、誰が書くか       打ち手一覧・差額処理基準・顧客への依頼計画
4 効果と費用       打ち手ごとに何が減り、いくらかかるか           施策別の効果試算表（業務オーナーと合意）・費用対効果
5 AI を置く場所    ルール・計算・AI・人の分担はどうなるか          役割分担表・自律度の設計
6 要件を書く       何をさせ、何をさせず、どう確かめるか           要件定義書
7 確かめて広げる   本当に当たっているか。どの型から任せるか        評価データ・影の運転の結果・段階導入の判定
```

順番に意味がある。**1〜4 を飛ばして 5 から始めると、濁った水を高い濾過装置で濾すことになる。** AI の出番は、清流化で残った例外に限られる。

## 1. 基礎知識

### 1.1 消込の仕訳

```
当たった         普通預金 1,000,000 ／ 売掛金 1,000,000
差額がある       普通預金   999,340 ／ 売掛金 1,000,000
                 売上値引       660                        （振込手数料を引かれた場合の一例）
当たらない       普通預金 1,000,000 ／ 仮受金 1,000,000     売掛金は残る
誤って当てた     普通預金 1,000,000 ／ 売掛金（別の請求）    正しい請求は未払いに見え、誤った請求は払われたことになる
```

- **仮受金の害は三つ。** 払った顧客が延滞に見えて督促の対象になる。本当の延滞が埋もれる。決算のたびに中身の説明を求められる。
- **誤消込の害は、見えないこと。** 帳簿は合って見えるので、翌月の不一致や顧客からの苦情で初めて発覚する。

### 1.2 消込に使う四種類のデータ

| データ | 出どころ | 中身 | 典型的な問題 |
|---|---|---|---|
| 入金明細 | 銀行（全銀形式のファイル、API） | 日付・金額・振込名義（半角カナ、途中で切れる） | 名義が略称・旧社名・個人名。何の支払いかは書いていない |
| 売掛金 | 各社の会計・販売システム | 請求番号・顧客・金額・期日 | システムごとに顧客コードが違う。請求の計上が遅れる |
| 入金予定 | 社内で作る | どの請求が、いつ、いくら、何を引かれて入るか | 多くの会社に存在しない。控除やリベートの合意は営業の手元にある |
| 支払通知 | 顧客が出す | 何の請求を、いくら、何を引いて払ったか | 出さない顧客がいる。形式がばらばら（PDF・メール・取引先サイト・FAX） |

**消込とは、入金明細と売掛金の間を、入金予定と支払通知で橋渡しする作業である。** 橋が無い入金ほど、人が推理することになる。

### 1.3 例外の類型地図

| 類型 | 典型原因 | 情報の発生場所 | 誰の手の中か | 代表的な打ち手 |
|---|---|---|---|---|
| 名義の不一致 | 略称、文字数切れ、旧社名、個人名、親会社の支払代行 | 顧客の振込登録 | 自社（対応表） | 振込名義を顧客マスタへ。支払人と請求先を分けて持つ。専用口座 |
| 複数請求の合算 | 月まとめ払い | 顧客の支払処理 | 顧客 | 支払通知の受け口を一本化。請求番号の記載依頼 |
| 手数料差引 | 振込手数料・海外中継手数料・決済手数料 | 契約・送金経路 | 自社 | 差額処理基準（許容額・勘定・承認者） |
| 控除・相殺・リベート | 協賛金・センターフィー・返品・年間リベート・買掛金との相殺 | 商談・契約 | 自社（営業・契約）＋顧客（明細） | 控除予定の登録、取引条件のマスタ化、支払案内の自動取得 |
| 請求の遅れ・誤り | 計上遅れ、請求前入金、訂正 | 各社の請求計上 | 自社 | 計上期限の設定、前受の扱いの基準化 |
| グループ会社の合算 | 顧客側で自社グループを一社扱い | 顧客の支払処理 | 顧客 | グループ共通の顧客番号、グループ一括の支払通知 |
| 一部入金・過入金・二重払い | クレーム、資金繰り、誤操作 | 顧客・営業 | 顧客 | 営業からの理由の連携。返金は承認つきの別手続き |
| 一括入金の分解 | 収納代行・口座振替・保証会社 | 代行会社の明細ファイル | 自社（受け取り方） | 明細ファイルを担当者経由でなく直接受ける |
| 外貨 | 為替差・中継銀行手数料 | 送金経路・社内方針 | 自社 | 許容額と勘定の基準化 |
| 手形・でんさい・ファクタリング | 支払手段の違い | 顧客の支払方法 | 自社＋顧客 | でんさいへの切替、通知のデータ連携 |
| 不明 | 一度きりの支払人 | 不明 | ― | 問い合わせ手順と滞留の見張り |

### 1.4 物差しの定義

| 物差し | 定義の注意 | 罠 |
|---|---|---|
| 自動消込率 | 行数で数えるか金額で数えるかを先に決める | 目標にすると、簡単なものから自動化され、重い例外が残る。当てにいく圧力で誤消込が増える |
| 誤消込率 | 自動確定のうち、後で誤りと判明した割合 | 抜き取り件数が少ないと、ゼロでも何も言えない（8.3 参照） |
| 手作業の時間 | 行数ではなく時間で持つ | 件数と時間は順位が違う |
| 仮受金の滞留 | 件数・金額・経過日数の三つで持つ | 金額だけだと、少額の長期滞留が見えない |
| 消込の締め日 | 第何営業日に全件を当て終えるか | 連結決算の締めに間に合うかで評価する |
| 誤った督促 | 払い済みの顧客に出た督促の件数 | 顧客の信用に直結する。ゼロを目標にできる |
| DSO（売上債権回転日数） | 売掛金 ÷ 売上 × 日数 | 消込の遅れで実態より悪く見えることがある |

## 2. 現状分析の設計

### 2.1 集める資料とデータ

- 請求元の一覧（会社ではなく、請求の作り方が違う単位で数える）
- 入金口座の一覧（銀行・口座・用途・どの請求元が使うか）
- 直近 1〜3 か月の入金明細と、消込の結果（どの請求に当てたか、差額の処理、仮受金に置いたもの）
- 仮受金の明細（件数・金額・経過日数）
- 顧客マスタ（各社）と、担当者の手元の対応表（名義帳のような「裏のマスタ」）
- 問い合わせの記録（誰に、何を、何日で）
- 差額処理・返金・督促の規程、職務分掌、システム構成

### 2.2 例外の分類は、機械で先に

一か月分を全件、人が読むのは作中の演出である。実務では**データで機械的に分けてから、残りを人が見る**。

```
機械で分けられる軸
  差額の有無           入金額と当てた請求額の差
  対応の形             1 入金：1 請求／1：N（合算）／N：1（分割）／N：M
  名義の一致           振込名義と顧客マスタのカナの一致・部分一致・不一致
  支払人と請求先       当てた請求の顧客と、名義の顧客が同じか
  通貨                 円・外貨
  入金の種類           振込・口座振替・収納代行・でんさい
  処理にかかった日数    入金日から消込日まで
残りを人が見る        上の軸で説明できない入金。サンプルで理由を付ける
```

時間は、**タイムスタディ（数日の実測）かワークサンプリング（抜き取り観察）**で取る。自己申告は、実態より少なく出る傾向がある。

### 2.3 分析の軸

例外ごとに、次の五つを一行に並べる。これが以降の全工程の土台になる。

| 軸 | 何を見るか |
|---|---|
| 件数 | 何行あるか |
| 時間 | 1 行あたり何分、合計何時間か |
| 滞留 | 仮受金に何日残るか |
| 発生源 | その情報はどこで生まれるか（商談・契約・請求・顧客の支払処理・銀行） |
| 誰の手の中か | 自社で決めれば直せるか、顧客に頼むしかないか |

**優先順位は、時間と、誰の手の中かの二軸で付ける。** 時間が重く、自社で直せるものが最優先。時間が重く、顧客の手の中にあるものは、依頼と AI による読み取りの組み合わせで攻める。

### 2.4 聞き方

- 現場には「何をしていますか」ではなく「今のは何ですか」と聞く。手順書に無い動きが本命
- 上流には「それはどこに書きますか」「その書いたものは、SSC に届きますか」と聞く
- 毎回聞かれている判断には「毎回、同じ答えですか」と聞く。同じなら、それは判断ではなく基準にできる
- 同じ質問を三人にする。食い違いが、暗黙の判断のありか

### 2.5 よくある罠

- **会社の数で数える。** 同じ会社でも請求の作り方が違えば別の川。数え間違えると打ち手が漏れる
- **件数だけで順位を付ける。** 名義の不一致のような軽い例外に資源が寄る
- **「上流に情報がある」を一括りにする。** 自社の中にある情報と顧客の中にある情報を混ぜると、打ち手の難しさを見誤る
- **先に AI の試作を作る。** 何が当たったのかを説明できない

## 3. 清流化の設計

### 3.1 五原則

```
1 発生源で鍵を付ける        請求番号・専用口座番号は請求を作るときに付ける
2 一度だけ、決まった形で書く  支払人・振込名義・支払条件・控除の合意を、生まれた場所で構造化する
3 人の受信箱を通さない       支払通知・控除明細・収納代行の明細を、担当者経由でなく SSC の受け口へ
4 判断を先に決める          差額の許容・勘定・承認者を基準にする。毎回同じ判断は決まりにする
5 濁りを上流に返す          例外を発生源ごとに数えて返し、費用も例外件数で配る
```

### 3.2 見直しの順番（ECRS）

| 順 | 問い | 入金消込での例 |
|---|---|---|
| なくす | その入金・その作業をなくせないか | グループ内の請求はネッティングで振込自体をなくす。紙の手形はでんさいへ |
| まとめる | ばらばらを一つにできないか | 38 口座を用途別に整理。グループ共通の顧客番号 |
| 入れ替える | 順番・担当を変えられないか | 督促の判定を消込の締め後に。控除の正否の判断を営業へ |
| 簡単にする | 残ったものを簡単にできないか | 差額処理基準で判断を不要にする |

### 3.3 差額処理基準に書く項目

```
対象         どの類型の差額か（国内振込手数料・海外中継手数料・決済手数料・端数など）
許容額       いくらまでを自動で処理するか（例：国内 1,000 円以下、海外 50 ドル以下）
勘定         どの勘定で処理するか（売上値引・支払手数料・為替差損益など）
型の条件     手数料の型に合うこと（よくある金額の一覧と一致する等）
承認         基準そのものの承認者（一件ずつではない）
例外         基準の対象外にする顧客・取引
見直し       何か月ごとに、誰が見直すか
```

### 3.4 顧客への依頼の設計

1. **対象を絞る。** 手作業の時間を多く生んでいる上位の顧客から。作中では上位 120 社で時間の半分
2. **時期を合わせる。** 請求書の様式変更、契約更新、システム切替の月に乗せる。単独の「お願い」にしない
3. **相手の得を先に言う。** 問い合わせの電話がなくなる。誤った督促状が届かなくなる
4. **動かない顧客を追いすぎない。** 協力率は半分程度を前提に試算し、残りは受け口での読み取りで拾う
5. **頼む人を決める。** 顧客との関係を持つのは営業。SSC は材料と文面を用意する

### 3.5 濁りの報告と、例外によるチャージバック

- **報告の列**: 会社・請求元／例外件数／うちその会社で生まれたもの（類型別）／消込に使った時間／仮受金の滞留（金額・日数）／前月比
- **費用の配り方**: 入金件数ではなく、例外件数（または例外にかかった時間）で配る。きれいな水を流す会社ほど安くなる
- **反発への返し**: 「原因」ではなく「場所」の話として出す。責める材料ではなく、直す場所の地図
- **注意**: 顧客起因の例外まで各社に課金すると不公平感が出る。自社で直せる類型と、顧客起因の類型を分けて表示する

## 4. 効果試算と費用対効果

### 4.1 施策別の効果試算表

```
列の定義
  類型 ／ いまの件数 ／ いまの時間 ／ 打ち手 ／ 残る件数（仮定）／ 残る時間 ／ 前提条件 ／ 合意した業務オーナー ／ 実施時期
```

- **「残る件数」は仮定であり、業務オーナーと一行ずつ合意する。** SSC だけで置いた数字は、上流が守らない
- 顧客に頼む打ち手は、協力率を仮定に明記する（例：協力率 50%）
- 実施時期で分ける。社内で済むものは半年、顧客に頼むものは一年、が目安

### 4.2 時間をお金に換える作法

| 効果の種類 | 計上してよい条件 | 例 |
|---|---|---|
| 人件費の削減 | 実際に人を減らす計画があるときだけ | 退職の不補充、配置転換で元部署の採用を止める |
| 支払いが減る | 残業代・派遣・外注が実際に止まる | 月初の派遣、休日出勤 |
| 採用しないで済む | 業務量の増加見込みが根拠つきで示せる | 入金が毎年 8% 増える分を今の人数で吸収 |
| 回収が早まる・貸倒が減る | 延滞の実態と回収策が紐づく | 90 日超の売掛金のうち一定割合の貸倒を防ぐ |
| 資金効果 | 回収日数の短縮 × 売上 × 調達金利 | 回収が 5 日早まる分の借入利息 |
| 締めの短縮 | 原則として金額にしない | 連結決算の早期化。定性効果として書く |

**人を減らさない計画で、人件費の削減を効果に入れない。** 三年後の振り返りで必ず崩れる。

### 4.3 費用項目

```
初期   顧客マスタの統合・名寄せ／専用口座（バーチャル口座）の導入／受け口の構築（メール・取引先サイトからの自動取得）
       エージェントの開発・試験・影の運転／既存システムとの連携／評価データの作成（人の時間も費用）
運用   AI の利用料（件数・文字量に比例）／保守／専用口座の手数料／ルール・手がかりの管理にかかる人の時間
       抜き取り確認にかかる人の時間／変更時の回帰試験
```

### 4.4 感度を見る

顧客の協力率（30%／50%／70%）と、エージェントの候補の的中率（80%／90%）の二つを振って、回収年数がどう動くかを一枚にする。**ぎりぎりの計画は、ぎりぎりだと書く。**

## 5. 推進と変革管理

### 5.1 利害関係者

| 関係者 | 関心 | 懸念 | 打ち手 |
|---|---|---|---|
| 経営（SSC・HD） | 生産性、中期計画の数字 | AI の効果が出ない | 清流化と AI の効果を分けて示す。人件費を効果に入れない理由を説明 |
| 各社の業務オーナー | 自部門の手間・費用 | 仕事が増える、責められる | 「場所の話」として報告。入力は一度だけ、既存の場で |
| 営業 | 顧客との関係 | 顧客に手間を頼みたくない | 上位顧客から、様式変更の月に、相手の得として |
| 顧客 | 支払いの手間 | 振込先変更の負担 | 誤督促がなくなる、問い合わせが減る |
| 消込の担当者 | 自分の仕事の行方 | AI に置き換えられる | 暗黙知を「会社の資産」として形にし、持ち主の役割を渡す |
| 内部監査 | 統制、証跡 | 説明できない自動処理 | 基準の承認、記録、変更管理、抜き取り件数を先に書く |
| 情シス・個人情報の担当 | セキュリティ、データの所在 | 外部 AI へのデータ持ち出し | 渡す項目、契約、保存場所を要件に入れる |

### 5.2 よくある抵抗と返し方

| 抵抗 | 返し方 |
|---|---|
| 「うちのせいだと言うのか」 | 原因ではなく場所の話。直せば費用が下がる仕組みにする |
| 「顧客にそんなことは頼めない」 | 全部には頼まない。上位から、様式変更の月に、相手の得として |
| 「AI で全部できるのでは」 | 誤消込の実例で、当てる量より間違えない質が大事だと示す |
| 「今のやり方で回っている」 | 回しているのは特定の人の暗黙知。その人が休んだ月の数字を見せる |
| 「監査が通らない」 | 監査の問いを要件に先に入れる。反対ではなく確認の場にする |

## 6. AI エージェントの設計

### 6.1 使う場所と、使わない場所

| 仕事 | 担い手 | 理由 |
|---|---|---|
| 明細の取り込み、専用口座・請求番号での照合 | ルール | 毎回同じ答え、説明できる |
| 手数料など基準内の差額処理 | ルール | 基準を承認済み |
| 金額の合う請求の組み合わせを全部数える | 計算 | 全件を数え上げられる。複数解の検知ができる |
| 支払通知・控除明細を読んでデータにする | AI | 形式がばらばらな文書の転記は AI の得意分野 |
| 組み合わせが複数あるとき、選ぶ手がかりを読む | AI | 支払通知・過去の癖・手がかりの照合 |
| 問い合わせ文の下書き | AI | 何が足りないかを添えて聞ける |
| 滞留の見張りと通知 | AI・ルール | 期限の近いものの抽出と要約 |
| 控除の正否、基準外の差額、返金 | 人（業務オーナー） | 判断であり、責任を伴う |

**AI は推理より転記のほうが間違えにくい。** 取水口で読ませ、河口では候補と根拠を出させるに留める。

### 6.2 構成

```
 [取込]  銀行明細・売掛金・支払通知・控除明細・収納代行明細
    ↓
 [正規化] 名義のカナ変換・全角半角・法人格の表記ゆれ・顧客マスタとの突合
    ↓
 [ルール] 専用口座／請求番号／入金予定との一致 → 基準内なら確定（段階 3）
    ↓ 決まらないもの
 [計算]  同一顧客・期日の範囲で、金額の合う組み合わせを全部数える
    ↓ 0 件・1 件・2 件以上を判定
 [AI]    支払通知・手がかり・過去の結果を読み、候補ごとの根拠を集める
    ↓
 [判定]  根拠の数と出どころから、確からしさ（高・中・低・なし）を付ける
    ↓
 [人]    候補を選んで確定。直した結果を記録
    ↓
 [記録・還流] 一件ごとの根拠と版を保存。直した結果からルール・手がかり・マスタの改善案を作る
```

### 6.3 確からしさの設計

- **AI の自己申告（「確信度：高」）は使わない。** 言い方と実際の的中率が一致する保証がない
- 根拠の数と出どころで決める。例：専用口座と入金予定の二つが独立に一致すれば「高」
- **較正する。** 影の運転で、高・中・低それぞれの実際の的中率を測り、ずれていれば区切りを引き直す。降水確率 70% の日に本当に七割降っているかを確かめるのと同じ

### 6.4 自律度

```
段階 0  見せるだけ
段階 1  候補を出し、人が選んで確定
段階 2  下書きを作り、人が確認して実行
段階 3  基準の中なら自動で確定し、人は事後に抜き取りで確認
（基準の外まで自動にする段階は設けない）
```

自律度は、エージェント全体ではなく**仕事ごと**に決める。読み取りは早く段階 3 に進めてよい。社外への送信は長く段階 2 に留める。

### 6.5 権限と信頼の境界

- エージェント専用の ID を払い出す。人の ID を借りない
- 読めるもの・書けるものを必要最小限に。書けるのは候補・下書き・通知・読み取り結果まで
- **外から来た文面はデータであって指示ではない。** 文書中の「承認済み」「優先処理せよ」で動作を変えない（隠し文字による指示の混入を想定する）
- 返金、振込先口座の登録・変更、顧客マスタの変更は権限の外に置く
- 返金や口座変更を求める文面は「なりすましの疑い」として人に回し、**登録済みの連絡先**に電話で確認する

### 6.6 データの扱い

- 外部の AI サービスに渡す項目を絞る。個人名を含む振込名義は個人情報として扱う
- 学習に使わせない契約か、保存期間と保存場所（国・地域）を確認する
- 渡す前に不要な項目を落とす、または置き換える
- 個人情報の担当部署と一緒に決め、要件定義書に書く

## 7. 要件定義書の目次（型）

```
1  目的と成功の物差し        何を減らし、何を増やさないか。物差しの定義と目標値
2  範囲                     やること・やらないこと
3  業務の流れ               現行と新しい流れ。人・ルール・計算・AI の分担表
4  自律の段階               仕事ごとの段階と、段階を上げる条件
5  入力                     読むデータの一覧、出どころ、更新頻度、信頼の扱い
6  出力                     候補の件数、根拠、確からしさの決め方、「分からない」の出し方
7  自動確定の条件            段階 3 の条件。「金額の一致だけで確定しない」
8  権限とデータの扱い        専用 ID、読み書きの範囲、外部サービスへの提供範囲、個人情報
9  引き継ぎ                 人に回す条件と、添える情報
10 記録                     一件ごとの記録項目、版、保存期間
11 評価と段階導入            評価データ、指標、影の運転の卒業条件、抜き取り件数
12 変更管理                 ルール・手がかり・AI の版・指示文の変更手続きと回帰試験
13 非機能                   処理量のピーク、処理時間、止まったときの手作業への戻し方
14 運用体制と還流            持ち主、見張り役、改善案の採否、上流への報告
15 統制と監査への対応         承認者、責任分担、監査で示す証跡
```

## 8. 評価と段階導入

### 8.1 評価データの作り方

- 過去 12 か月の人の消込結果から、正解つきのデータを作る。誤りが後で見つかったものは直してから使う
- ベテランが「迷った」入金を別に集める（作中の 50 件）。難問だけの試験問題になる
- 類型ごとに件数の偏りを確認し、少ない類型は意図的に足す

### 8.2 指標

| 指標 | 平易な意味 | 使いどころ |
|---|---|---|
| 候補の的中率（上位 3 件） | 出した候補の中に正解が入っている割合 | 段階 1 の有用性 |
| 確定の正確さ | 自動で確定したもののうち、正しかった割合 | 段階 3 の安全性。誤消込率はこの裏返し |
| カバー率 | 候補を出せた入金の割合 | 「分からない」が多すぎないか |
| 較正のずれ | 「高」と言ったものの実際の的中率 | 確からしさの信頼性 |
| 読み取りの正確さ | 支払通知から項目を正しく拾えた割合 | 取水口の品質 |

### 8.3 抜き取り件数（3 の法則）

誤りがゼロで n 件確認したとき、誤りの割合の上限の目安（95%）は **3 ÷ n**。

```
確認した件数     言える上限の目安
      100       3%
    1,000       0.3%
    3,000       0.1%
    6,000       0.05%
```

「誤消込 0.05% 以下」を約束するなら、誤りゼロで 6,000 件を見る必要がある。毎月 1,000 件なら半年。**抜き取り件数は、要件定義書に書く約束の一部である。**

### 8.4 影の運転の卒業条件（例）

- 上位 3 件の的中率 95% 以上
- 確からしさ「高」の誤り 0.1% 以下（判定に足る件数で）
- 読み取りの正確さが類型ごとに基準以上
- 処理時間がピーク時の要件内

### 8.5 変えるたびに確かめる

ルール・手がかり・AI の版・指示文のどれかを変えるたびに、評価データで回帰試験を行う。AI の提供元が版を更新する場合も同じ扱いにする。

## 9. 作るか買うか

**要件を先に書き、製品はその物差しで選ぶ。** 先に製品を見ると、製品の説明書が要件定義書になる。

| 比較軸 | 確かめること |
|---|---|
| 要件の充足 | 要件定義書の各行を満たすか。満たさない行は、作って足すか業務を合わせるか |
| 銀行・会計との連携 | 使っている銀行・会計システムとの標準連携の有無 |
| 確からしさの根拠 | 候補の根拠を示せるか。自己申告の数値だけではないか |
| 統制 | 承認・記録・変更管理の機能。監査に出せる証跡 |
| データの扱い | 保存場所、学習利用の有無、個人情報の扱い |
| 費用 | 初期・月額・件数課金。5 年の総額 |
| 撤退のしやすさ | ルール・手がかり・評価データを持ち出せるか |

## 10. 会計・税務・法令の確認一覧

| 論点 | 要点 | 確認先 |
|---|---|---|
| 差額の会計処理 | 手数料・端数・為替差を、どの勘定で処理するかを基準化 | 経理・監査人 |
| 仮受金の管理 | 滞留の期限、調査手順、長期滞留の処理 | 経理・監査人 |
| リベート・協賛金 | 収益認識基準では、変動対価や顧客に支払われる対価として売上から控除する扱いが論点になる | 経理・監査人 |
| 振込手数料の差引（受け取る側） | 売上値引きとして処理する方法が一般的。税込 1 万円未満の返品・値引きは返還インボイスの交付が不要 | 税理士・国税庁の資料 |
| 振込手数料の差引（払う側） | 中小の受託事業者への支払いで手数料を差し引くと、代金の減額として問題になる。2026 年施行の改正下請法（取適法）で扱いが厳しくなっている | 公正取引委員会の運用基準・法務 |
| 手形 | 改正下請法（取適法）で、中小の受託事業者への手形払いは原則として禁止。業界としても紙の約束手形の廃止が進む | 公正取引委員会・取引銀行 |
| 控除・協賛金の妥当性 | 根拠のない控除の押しつけは、優越的地位の濫用の論点になりうる | 法務 |
| 支払通知の保存 | メールや取引先サイトで受け取った支払通知は電子取引データとして電子保存が必要 | 経理・電子帳簿保存法の要件 |
| 個人情報 | 個人名義の入金データを外部 AI に渡すときの委託・越境移転の扱い | 個人情報の担当・法務 |
| 外貨 | 被仕向送金の手数料、為替換算の方針 | 経理・取引銀行 |
| 内部統制 | 自動処理の基準承認、IT 全般統制（変更管理・アクセス管理） | 内部監査・監査人 |

> この表は論点の地図であり、結論ではない。条文・運用基準・通達の最新版を必ず確認する。

## 11. 現場で使う問い

**現状を数えるとき**
- 請求書を出している単位はいくつあるか。会社の数と違うか
- この一行は、どこで生まれたか。銀行は運んだだけ
- いま何をしたか（「今のは何ですか」）
- 件数で一番多いものと、時間で一番重いものは同じか

**生まれた場所をたどるとき**
- その決めごとは、どこに書かれているか
- それは SSC に届いているか。届いていないなら、誰の受信箱で止まっているか
- その情報は自社の中にあるか、顧客の手の中にあるか
- 毎回同じ答えなら、それは判断か、決まりか

**清流化を設計するとき**
- その作業を、なくせないか
- それを書く人は誰で、それは一度だけか
- 顧客に頼むなら、相手の得は何か。どの月に乗せるか
- 例外の費用は、誰に見えているか

**AI を置くとき**
- それはルールでできないか。計算でできないか
- 間違えたとき、見えるか、見えないか
- 分からないときに「分からない」と言えるか
- 確からしさは、何を根拠に決めているか
- 外から来た文面に、指示が紛れていたらどうなるか

**要件を書くとき**
- 承認者は誰か。一件ずつか、基準か
- 何件確かめれば、約束した数字を言えるか
- 止まったとき、人の手で締められるか
- 効果に入れてはいけない数字が混ざっていないか
